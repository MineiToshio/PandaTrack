# Glossary

This document is the canonical glossary of product terminology used across PandaTrack. Both languages are canonical: every team-facing surface must use these exact terms.

If a term you need is not listed here, add it before introducing inconsistent wording in code, copy, or documentation.

## How to use this glossary

- **Source of truth.** When the product code, copy, or documentation references one of the concepts below, use the exact term in the column for that locale. Do not introduce synonyms.
- **Applies to.** UX copy (`src/i18n/locales/**`), in-product labels, marketing copy, product docs (`docs/product/**`), GitHub issues, FRDs, work orders, ADRs, and PR descriptions.
- **Locale-paired.** When a string exists in both `es` and `en`, use the matching pair from this table. Do not translate between the two using a thesaurus; use this glossary.
- **Code identifiers.** Code identifiers (variables, types, files, routes) follow the **English** column. Repository code is English-only per `english-code-only.mdc`.
- **Update process.** When introducing a new product concept, add the term here in the same change that introduces it. When a term is renamed, update existing strings, identifiers, and docs in the same change and remove the old term.

| Money paid to a tienda that no pedido or producto currently claims.                                                  | **dinero sin asignar**            | **unassigned money**            | Added 2026-08-20 (**ADR 0033**, implemented the same day, uncommitted, staging). Names, for prose and for the rest of this money vocabulary, the same money the **asignación** entry already calls a pago's own undeclared remainder, and that the store aside's progress block, as things stand today, nets as **a cuenta** / **on account**, a line that is scheduled for retirement and superseded by this exact figure (**ADR 0033**, added 2026-08-20, implemented the same day, uncommitted, staging). It reduces **nobody's debt** until assigned: this is the fix for the failure where a pedido closes taking its debt but leaving its payment behind. Closing a pedido consumes it automatically, up to that pedido's saldo pendiente (`min(saldo, sin asignar)`, oldest pedido first in a batch, never a proportional split); the collector is asked first, and if he skips the question it is applied anyway, because understating a debt is the silent failure and overstating is the visible, self-correcting one. When a store-level pago cannot be assigned in full at the moment it is recorded (the deliberate "no sé todavía" escape from the now-mandatory assignment), the money is described as **aparcada** / **parked** rather than merely unassigned: it sits in a suspense-account-like state until the collector, or the pedido-closing consumption above, resolves it. Prefer **aparcada** in copy for that deliberate holding state; **sin asignar** for the plain fact that no pedido claims it yet. Distinct from **a favor** (that is negative debt, money the collector overpaid) and from **sin desglosar** (money already assigned to a pedido but not to one of its productos). | When a pedido is expected to arrive, stated with the precision it was declared with.                                 | **ventana de llegada**            | **arrival window**              | Added 2026-08-16 (**ADR 0030**, `FR-05-56`). `Order.expectedDeliveryFrom`/`To` as the collector entered them, and the granularity is part of the term: a range spanning a whole month IS the month and is written as such ("sept", "sept 2027"), because the order form's own presets write it that way; _(The month name is whatever `Intl.DateTimeFormat(locale, { month: "short" })` returns, never a hand-written table. Docs written before 2026-08-17 said "sep", which the app has never rendered.)_ a stated day, a range of whole months and an irregular window keep their own shape. The verb pair is fixed and identical on every surface, and each opens a line, so it is written in sentence case: **Llega {ventana}** / **Arrives {window}** while the window is still ahead, **Esperada {ventana}** / **Expected {window}** once it has passed on something still awaited; **Sin fecha estimada** / **No estimated date** when there is none. _(Revised 2026-08-17, **ADR 0030 §3.1**: "Esperada" no longer covers the answered case. It survives on the per-order list, where an order can be past its window and still waiting; on the "Por tienda" row it has no caller left, because there the only way to be past the window and not late is to have arrived.)_ _(Revised 2026-08-17: these were lowercase when first shipped, copied from the embedded phrasing of the per-order list, where lowercase is correct because the phrase sits inside a sentence. On the "Por tienda" row it starts one.)_ The state in which an observed event has answered the prediction is **`resolved`**, and since 2026-08-17 (**ADR 0030 §3.1**) it has words of its own, one per delivery state: **Ya llegó a la tienda** / **Already at the store** and **Ya está en camino** / **Already on its way**, with no ventana in either. It used to reuse **Esperada {ventana}**, and the collector read that as a defect ("why does it say expected 12 jun and not overdue?"): the line stated a prediction and never named the event that answered it, while the chip that accounts for it sits three columns away. The words do not repeat that chip (**Listo en tienda** / **En camino**) because a chip names a STATE and this line answers "when does it get here?". At ORDER level the same fact is written **ya llegó a la tienda** / **already at the store**, lowercase because there it is embedded after a `·` (**ADR 0030 §3.2**). It covers **llegada a la tienda** / `ARRIVED_AT_STORE` (see that entry, which keeps owning the chip "Listo en tienda") **and** the shipment already in transit, which is exactly why it is not named after either one. It deliberately does **not** use **Saldado** / **Settled**: that word belongs to **marca de pagado** and to the arithmetic that proves a producto paid, and it is rendered on the very same row. Late-ness is a fourth value of the SAME slot rather than a badge beside it, so on that row **Atrasado {n} días** / **Overdue {n} days** (and **Atrasado {n} meses** / **Overdue {n} months** from 60 days) is written **instead of** the ventana, never next to it: on a late producto the estimate is the question and the delay is the answer. It is `warning`-toned and never earns a second tone. The abbreviated **Atrasado {n}d** form is the CHIP wording, kept for the per-order list and the detail where a pill pays for every pixel; the arithmetic behind both is one function. There is no user-facing word for "close to arriving": that state was merged into the ordinary **Llega {ventana}**, because the ventana already says it. |

## Domain rules tied to terminology

### Producto / product is an atomic shippable unit

Each `producto` (a line inside a `pedido`) represents **one shippable unit**, even when its `cantidad` (quantity) is greater than `1`. The data model treats `producto` as atomic for fulfillment: every `producto` is either fully included in a given `entrega` or not included at all. Fractional fulfillment of a single `producto` across multiple `entrega`s is **not supported**.

Consequences for product surfaces:

- When a user expects different units of the same SKU to arrive in separate `entrega`s, they must enter each unit as a **separate `producto`** with `cantidad = 1` at the time of `pedido` creation. Quantity greater than `1` should be reserved for units that will arrive together.
- The `entrega` create flow must not expose a quantity selector per `producto`; the checkbox represents the entire `producto`.
- The order form must surface this rule contextually (e.g. an inline tooltip near the products section) when at least one `producto` in the form has `cantidad` greater than `1`, so the user has the chance to split before saving.
- If the product later needs partial fulfillment, that is a schema change (adding `quantity` to `DeliveryOrderItem`) tracked in `frd-05` and `frd-08`, not a UI tweak.

## Anti-patterns to avoid

- `Capturar de WhatsApp`, `captura rápida`, `Nuevo desde captura`: retired names for `crear desde imagen`. The feature accepts any image source, so a WhatsApp-specific name lies about what it takes.
- `extracción`, `crédito`, `token` as the user-facing name of a consumed unit: always use `foto`. This veto is scoped to the photo quota; it does not ban the word "crédito" everywhere, but money surfaces still say **a favor** (see the term above), not "crédito", to avoid ever reading as a second, unrelated consumed-unit balance next to the foto quota.
- The `Capture` suffix in code identifiers for image-intake work: use `imageIntake` / `OrderImageIntake`. `Capture` already means something else in the repository's analytics vocabulary and creates silent collisions when searching.
- `Separar en tomos`: always `Separar en productos`. `producto` is the canonical name of a pedido line, and "tomos" would tie the interface to manga when PandaTrack targets general collecting.
- `orden` / `órdenes` (es) — always use `pedido` / `pedidos`.
- `envío` / `envíos` (es) — always use `entrega` / `entregas`.
- `shipment` / `shipments` (en) — always use `delivery` / `deliveries`. Marketing copy that references the broader concept of physical shipping is the only allowed exception, but keep the in-app feature name as `delivery`.
- Mixing `purchase` and `order` in the same surface. New work should standardize on `order`.

### Exception: "envío" / "shipping" as an attribute, not an entity

The ban above applies to `envío` / `shipping` when it names the **feature** (the entity is `entrega` / `delivery`). It does not apply when the word describes an **attribute** of a `delivery`, such as a shipping date or a shipping cost — English commonly qualifies these as "shipping date" / "shipping cost" the same way Spanish uses "fecha de envío" / "costo de envío". Existing attribute-level labels in `deliveries.json` and `orders.json` (for example a shipping-date or shipping-cost field label) are correct as written and do not need to be renamed to "delivery date" / "delivery cost". Only the entity name is reserved for `entrega` / `delivery`; do not introduce a new top-level "envío" / "shipment" feature, route, or model.
