# FRD-05 Order and Payment Tracking

## Overview

Define the collector-facing order and payment workflow for the PandaTrack MVP.

This FRD covers order creation, item capture, derived totals, per-order exchange-rate context, private notes, payment progress, list/detail surfaces, and the business rules that distinguish an order's financial state from its delivery state.

## Domain Goal

Give collectors one reliable place to record what they bought, what it cost, how much has been paid, and whether the order is still open, partially delivered, completed, or cancelled.

## Current State

### Implemented

- order detail at `/orders/[id]` ([`BP-02 · WO-05`](bp-02-order-workspace-and-list-experience/work-orders/wo-05-order-detail-view-private-note-payments-panel-and-action-menu.md)): two-column layout on `lg+` (items + private note left; payments + read-only history right, sticky rail), payments panel with optimistic updates, scroll-to-form when opening add-payment, private note; automatic order history is **read-only** (no per-entry delete; see `FR-05-22` / `BR-05-09` below).
- **Store-level payments (2026-08-08, `docs/design/decisions/0025-store-level-payments-declared-allocations.md`):** money is recorded against the **store** (`StorePayment`), with an optional, declared **allocation** to one or more orders/items (`PaymentAllocation`) rather than always to a single order. Adding a payment from the order detail still records amount + date and pre-assigns the whole thing to that order (`FR-05-17`); the **store payment sheet** (`FR-05-42`) authors a payment against several orders/products at once from the orders "Por tienda" view or the store detail page. Per-order payment percentage left the UI (`FR-05-31`, `FR-05-41`); the store's own debt, per currency, is now the primary money figure (`FR-05-43`).
- private app navigation already exposes an `Orders` entry point; pre-orders have no separate nav item or route and live inside that section (`BR-03-02`)
- [`FRD-07`](../frd-07-user-settings/frd-07-user-settings.md) already defines a user-level base currency preference that this domain can consume
- store discovery and store detail flows already exist, which makes store selection a prerequisite rather than a parallel domain problem
- order persistence and human-readable order identifiers (`ORD-YYYYMMDD-NN`)
- create flow as a 3-step wizard (data → products and costs → confirm) with forward gating and free backward navigation, plus a reactive summary rail; edit flow as an all-open form with store and currency locked
- spreadsheet-style item entry with quantity, optional unit price, and optional product type
- required total-cost capture with discrepancy confirmation when item totals do not match (two-option modal — see `FR-05-13`)
- one exchange-rate context per order when order currency differs from the user's base currency, with a "Today" prefill helper backed by the published-rates provider (`FR-05-16`)
- payment records with remaining-balance guidance and delete support; add-payment is an inline expand inside the payments card, and deletions go through a destructive confirmation modal and are awaited (no optimistic update, no undo toast)
- order detail view with inline private note editing (autosave on blur, ~800ms debounce)
- orders list with filters, overdue-delivery signals, and payment-progress summaries; default sort is most-recent first (`FR-05-28`)
- currency reconciliation: `Needs currency update` filter, `pendingFxCount` derived in `getOrdersList`, and the shared `FxReconciliationModal` bulk flow

## User Stories

### US-05-01 Track what I committed to buy

As a collector, I want to save an order with store, dates, currency, and products so I stop depending on memory or chat history.

### US-05-02 Mix quoted totals and itemized totals

As a collector, I want to either enter a full quoted total manually or derive it from item prices so PandaTrack still fits stores that quote orders in different ways.

### US-05-03 Understand what I still owe

As a collector, I want to register payments over time and immediately see the amount assigned to each order and its remaining balance, plus my overall debt with each store, so surprise balances do not catch me off guard.

### US-05-04 Spot risky orders quickly

As a collector, I want the orders list to show overdue estimated-arrival ranges and delivered-but-unpaid cases so I know which orders need attention first.

## Functional Requirements

- `FR-05-01`: The system must use `Order` as the primary tracked transaction entity for the collector workspace.
- `FR-05-02`: An order must belong to exactly one store.
- `FR-05-03`: An order must expose a human-readable identifier in the format `ORD-YYYYMMDD-NN`.
- `FR-05-04`: An order must require an order date and prefill it with the current date on create.
- `FR-05-05`: An order must support an expected delivery date range.
- `FR-05-06`: An order must support one or more order items.
- `FR-05-07`: Each order item must store name and quantity.
- `FR-05-08`: Each order item quantity must default to `1` and must be required.
- `FR-05-08a`: Each order item is an **atomic shippable unit**: it is either fully included in an `entrega` or not included at all. Fractional fulfillment of a single order item across multiple `entrega`s is not supported in the MVP. Collectors who expect units of the same SKU to arrive in separate `entrega`s must register them as separate order items with `quantity = 1`. Quantity greater than `1` is reserved for units that will arrive together. The order form must surface this rule contextually (for example a tooltip in the products section) when at least one order item has `quantity > 1`, so the collector has the chance to split before saving. See `docs/product/glossary.md` for the canonical statement of the rule and the upgrade path if partial fulfillment is later prioritized.
- `FR-05-09`: Each order item may store an optional unit price.
- `FR-05-10`: Each order item may store an optional product type selected from the shared catalog.
- `FR-05-11`: Each order must store a required total cost.
- `FR-05-12`: The system must derive the itemized total as the sum of `quantity x unit price` across all items that have prices.
- `FR-05-13`: When every order item has a unit price and the derived itemized total differs from the entered total cost, the save flow must present a modal that lets the user either go back and correct the order or save with the entered total anyway. **Redesign change (CB-02, 2026-05-17):** the modal now offers **two** options ("Go back and correct" / "Save anyway") instead of three. The "replace with the derived total" option was dropped because the entered total is always authoritative; auto-replacing it created confusion.
- `FR-05-14`: Each order must store an order currency selected by the user.
- `FR-05-15`: The order currency field must default to the user's saved base currency when present.
- `FR-05-16`: When the order currency differs from the user's base currency, the order form must require one exchange-rate value that converts from order currency into base currency. **Redesign note:** the field offers a "Today" prefill helper that calls the published-rates provider (ExchangeRate-API open endpoint, no API key, 5s timeout) from the client to suggest the current rate; the collector can still edit the value. The rate is oriented as "how many base-currency units equal 1 order-currency unit". The provider's terms require a visible credit wherever a fetched rate is shown, so every surface that offers the helper renders one.
- `FR-05-17` **(revised 2026-08-08, store-level payments — ADR 0025):** Order detail must let the user add and delete payment records over time. "Add payment" is an inline expand inside the payments card (not a separate modal). **Revised 2026-08-14 (F1):** the form asks for money and nothing else, an amount and a date. The amount field offers three quick-picks over the REMAINING balance, **"Todo · {amount}" / "50%" / "20%"** (536 of the collector's 626 recorded payments covered the whole balance, and the 18-25% band holds 29 of the 79 partial first payments; the percentage chips show the percentage, with the resulting amount in their `aria-label`). The date renders folded to a "Hoy, {date} · Cambiar" line while it still reads today, unfolds on demand or when the form refuses the date it holds, and never folds again once touched. The submit button names the outcome ("Registrar {amount}"). The panel folds in the same tick as the submit on desktop as it already did on mobile (Optimistic Confirmation), so a refusal is reported by toast from the coordinator. What it writes is a **store payment pre-assigned to this order**: `addOrderPayment` keeps its exact name and signature but is now a thin order-scoped wrapper over `createStorePayment`, raising one `StorePayment` with a single `PaymentAllocation` covering the whole amount (narrowed to the order's own item when it has exactly one). A payment that covers more than one order, or names a specific product without covering the whole order, is authored from the **store payment sheet** (`FR-05-42`), not from this inline form. **Revised 2026-08-21 (`BR-05-32` client mirror, live browser pass of the 2026-08-20 reconciliation package):** the quick-picks and the amount-exceeds gate bound the REMAINING balance against `openBalanceMinor` (net of any `StoreAccountAdjustmentLine`), not the order's gross `totalCost − allocated`, so on a written-off order "Todo" can no longer offer, and the field can no longer accept, an amount the server was always going to refuse. The `EXCEEDS_BALANCE` ceiling itself (`FR-05-19`) was already net server-side since `ADR 0034`; this closes the client-side gap where the form still gated on the gross figure and, on refusal, echoed that same gross number back as both sides of a self-contradicting sentence ("180 exceeds 180"). Two new states follow: a typed amount inside the gross balance but above the net one, and a server `EXCEEDS_BALANCE` refusal on such an order, both render a distinct `amountExceedsBalanceReconciled` copy naming the reconciliation rather than repeating the (correct but confusing) gross figure; when the net balance is exactly 0 the amount field and submit button are disabled outright, with the same copy shown up front. The order's own gross "Falta" figure and "still owed" chip are unchanged (`FR-05-35`): only this form's WRITABLE ceiling moved.
- `FR-05-18`: Each payment record must store amount and payment date.
- `FR-05-19` **(revised 2026-08-08):** The payment flow must refuse a payment whose amount, once declared against this order, would exceed the order's current remaining balance (`EXCEEDS_BALANCE`), **and** must separately refuse a payment larger than what the collector still owes the order's **store** in that currency (`STORE_DEBT_EXCEEDED`, `FR-05-43`). Both ceilings are checked inside the same transaction, before any write (ADR 0022).
- `FR-05-20` **(revised 2026-08-08):** The order detail view must show the amount **assigned** to this order (`Order.allocatedAmountMinor`: the sum of this order's `PaymentAllocation` rows) against its total, and the remaining unassigned balance. A per-order payment **percentage** is no longer shown as a standalone figure; the hero instead shows "Asignado {X} de {Y}" with a progress bar while something is assigned, or a link into the store's own debt when nothing is (`FR-05-41`).
- `FR-05-21`: The order detail view must expose one inline-editable private note field that can be saved without entering full order edit mode, including saving an empty value to clear the note. **Redesign note:** the note autosaves on blur with a ~800ms debounce and shows a "saved Ns ago" indicator; the save waits for server confirmation (not optimistic).
- `FR-05-22`: The order detail view must expose an automatic history list that records major order lifecycle events. **As implemented (2026-04-24):** the list is **read-only**; users cannot delete individual history entries from the UI (aligned with [`WO-05`](bp-02-order-workspace-and-list-experience/work-orders/wo-05-order-detail-view-private-note-payments-panel-and-action-menu.md) and migration `20260423000000_simplify_order_history_event_types`).
- `FR-05-23`: The order detail view must expose `Create delivery` as the primary action plus secondary affordances for `Edit`, `View store`, `Cancel`, and `Delete` as appropriate for the order status. **Redesign change (ADR 0011, 2026-05-12):** the secondary affordances are presented as an inline "Actions" card at the foot of the detail scroll (action rows: Edit, Cancel, Delete in red), not as a split button or an overflow (`⋯`) trigger in the header. This applies on both desktop and mobile.
- `FR-05-24`: An order may be physically deleted only when none of its items is linked to a non-cancelled delivery. When the rule is not met, the delete affordance must be rendered as disabled with a tooltip that explains the collector must first unlink the affected items from their delivery.
- `FR-05-25`: An order may be cancelled only when none of its items is linked to a non-cancelled delivery. When the rule is not met, the cancel affordance must be rendered as disabled with a tooltip that explains the collector must first unlink the affected items from their delivery. Cancelling an order moves it to `CANCELLED` without removing its historical record.
- `FR-05-26`: The orders list must support filters for order-date range, store, product type, status, and free-text product-name matching.
- `FR-05-27`: Orders list filters must persist in the URL and render removable chips in the same interaction pattern used by `Stores`.
- `FR-05-28`: The orders list must sort by **most recent order date first by default**. **Redesign change (CB-01):** the original default was oldest-first; it was flipped because collectors manage recent orders first while older ones are usually closed. (The sort control still offers oldest-first and other options.)
- `FR-05-29`: Each order card in the list must show store identity, order date, status, expected delivery range, total cost, and payment progress.
- `FR-05-30`: The orders list must visually indicate when an order has passed its expected delivery range without being completed.
- `FR-05-31` **(revised 2026-08-08, store-level payments):** Each order card must expand to show the order items associated with the order. The collapsed card no longer carries a payment-progress bar, a paid-versus-total percentage, or a payment-state filter pill: individual payment records (declared allocations) are accessible from the order detail view, and the aggregate per-store, per-currency debt is accessible from the orders list's "Por tienda" view (`FR-05-44`) and the store detail page. The list still shows a **"Pago completado"** success chip, but only once (`FR-05-35`), and a completed order that still owes money carries a second **"Saldo pendiente"** chip beside its status chip (`FR-05-35a`). Neither is a payment percentage.
- `FR-05-32`: Order status must be derived from fulfillment outcomes rather than directly edited by the user.
- `FR-05-33` **(revised 2026-08-08, revised 2026-08-20, independent by default with an explicit arrival shortcut, `ADR 0032`):** Payment state must remain conceptually distinct from order fulfillment state **by default**. Under store-level payments, "payment state" for an order means how much money is **assigned** to it (`Order.allocatedAmountMinor`), not a percentage computed against a payment ledger that belongs to the order; it is still never persisted as, or allowed to influence, `OrderStatus`. The one deliberate exception is the arrival shortcut, "Ya pagué el resto" (`FRD-08 · FR-08-39`): when the collector leaves it checked, marking a delivery `DELIVERED` additionally authors a store payment, but as a **second, separate transaction** that runs only after the delivery transaction has already committed (`FRD-08 · FR-08-42`, `ADR 0032`), never as a side effect computed inside the delivery write itself. A fulfillment change still never implies a money change in the same commit, and unchecking the box, or the payment transaction failing, leaves the delivery recorded with payment state untouched.
- `FR-05-34` **(revised 2026-08-08, revised 2026-08-20, `ADR 0032`):** When all products linked to an order are delivered, the order must move to `COMPLETED` even if it still has money outstanding (`allocatedAmountMinor < totalCost`). The delivery-triggered settlement shortcut (`FRD-08 · FR-08-39`) does not change this rule: its payment is written in a separate transaction that runs after the delivery has already committed (`FRD-08 · FR-08-42`), so the `COMPLETED` transition itself never waits on, blocks for, or reverses because of that payment succeeding, failing, or being skipped.
- `FR-05-35` **(revised 2026-08-11):** Completed orders with money outstanding must still show a visible unpaid signal in both list and detail surfaces. The "paid" signal (list chip, detail "Pago completado" chip) fires only when the order is **fully assigned** (`allocatedAmountMinor >= totalCost`), never at a partial percentage: there is no "mostly paid" success state under this model.
- `FR-05-35a` **(added 2026-08-11):** On the **list**, that signal is a second chip, **"Saldo pendiente"** (warning tone, `alert-triangle`), rendered **beside** the status chip on both the desktop row and the mobile card, never replacing it. It carries the same wording, tone and icon as the order detail hero's own chip, so one pedido reads the same on every surface. It appears only on `COMPLETED` orders that still owe money: on an active pedido a balance is the ordinary state, so flagging those would tint the whole list and the signal would stop meaning anything; a `CANCELLED` pedido owes nothing whatever its total says (`ADR 0025`, debt sums non-cancelled orders only).
  **Why this is written down as its own requirement:** `FR-05-35` had said "list and detail" since 2026-08-08 and only the detail ever complied. The list kept showing a lone green "Completado", so 16 delivered pedidos carrying 1,780.65 of real debt were invisible for years, and the gap was found by reading the data, not the screen. The chip is **binary** on purpose. It is not a reintroduction of what `ADR 0025` retired: there is no percentage, no paid-versus-total figure and no per-row progress bar, because none of those are facts under store-level payments. "Money is still owed on this one" is. **Unaffected by the open-order debt scoping of `FR-05-61` (`ADR 0033`, noted 2026-08-20):** this chip and the hero's own "Pago completado" / balance state (`FR-05-35`, `FR-05-41`) read this order's own `totalCost` against its own `allocatedAmountMinor`, never the store's aggregate debt. Scoping the store's displayed debt to open orders changes what a store is shown to owe, not what an individual order is shown to owe, so a `COMPLETED` order with a balance keeps carrying this chip exactly as before.
- `FR-05-36`: The orders workspace must support a `Needs currency update` filter that returns orders requiring exchange-rate reconciliation to the collector's current base currency.
- `FR-05-37`: Exchange-rate reconciliation eligibility must be based on budget-impact periods from the current month onward, not only order status; completed orders that still impact current/future payment periods remain eligible.
- `FR-05-38`: When the collector changes base currency, the product must support bulk exchange-rate reconciliation grouped by currency pair (`from -> to`) and allow deferring reconciliation for manual per-order updates later.
- `FR-05-39`: The collector must be able to flip each order item between `pending in store` (`NONE`) and `ready at store` (`ARRIVED_AT_STORE`) directly from the item's state chip, **on the order detail and on the orders list alike, in both the card and the table layout** _(list surfaces added 2026-08-05)_, as a pre-delivery readiness marker. The toggle is available only while the item is **not** linked to a non-cancelled delivery and the order is **not** `CANCELLED`; in those cases the pill is read-only with an explanatory disabled label (delivery-owned `in_transit` / `delivered` states must not be editable from the order, and a cancelled order is frozen). This state is the same `OrderItemDeliveryState` that delivery eligibility reads (`NONE` / `ARRIVED_AT_STORE` are both eligible) and that `FRD-08` consumes; flipping it does not by itself change the derived `OrderStatus` (both values map to `open`).
- `FR-05-39a`: The list chip is the control, not a second affordance beside it. Marking a product ready is a one-bit change a collector usually makes for several products in a row, and routing it through the order detail cost a navigation and a return trip each time; a separate button next to the chip would have said the same thing twice. The mutation is optimistic on both surfaces (`optimistic-client-updates.mdc`) and reverts on failure, because the round trip is the whole interaction when several are flipped in sequence. On the card, where the entire surface is a link to the order, the chip must not navigate.
- `FR-05-40` **(revised 2026-08-08):** The edit flow must refuse to lower an order's `totalCost` below its own `allocatedAmountMinor` (the sum of `PaymentAllocation` rows declared against it, not the store's whole payment ledger). The form blocks it client-side and the `editOrder` mutation enforces the same guard server-side (rejecting with `TOTAL_BELOW_PAID`), so the remaining/unassigned amount can never be driven negative. To reduce the total past what is assigned, the collector must first delete or reduce the relevant declarations.

### Store-level payments (added 2026-08-08 — see `docs/design/decisions/0025-store-level-payments-declared-allocations.md`)

- `FR-05-41`: The order detail hero must show, below the order's total, either (a) "Asignado {X} de {Y}" plus a progress bar (`allocated/total`) when this order has at least one `PaymentAllocation`, or (b) a link into the store's own debt in this order's currency ("Deuda de la tienda: {Z}", or "A favor: {|Z|}" in the success tone when the store owes the collector instead) when it has none. A "Pago completado" chip joins the status chips once `allocatedAmountMinor >= totalCost` (`FR-05-35`).
- `FR-05-42` **(revised 2026-08-10, revised 2026-08-20, `ADR 0033`: a payment with no declaration is no longer a legitimate outcome on this surface):** The product must offer a **store payment sheet** (`StorePaymentSheet`) that records a payment against a store and lets the collector declare, in the same submission, what part of that store's standing orders it covers. The sheet has two panels inside one modal: **Pago** (amount, date, currency when it applies, note) and **Asignación**, entered explicitly; the payment panel is the default path and a payment with no declaration at all was, until now, a legitimate result ("on account") **(superseded 2026-08-20 by `FR-05-58` on this surface only: the sum of the Asignación panel must equal the payment's amount, and a remainder the collector cannot attribute goes to the store's parked pool through the deliberate "no sé todavía" action of `FR-05-60` instead of being left implicit. `BR-05-31` keeps the order-scoped inline form of `FR-05-17` unchanged, where money can never be orphaned, so "on account" survives there)**. The allocation panel presents a **flat list** with no per-order container, whose unit is the **payable line**: one per product with a balance and, when an order's balance does not fit inside its products, a **"Resto del pedido"** line (see `FR-05-42a`). Each line accepts a typed amount, and its shortcut cell is a fill control (labelled "Máx.", printing no figure) that writes the largest amount assignable without invalidating the draft; the amount it will write lives only in the control's accessible name, computed once via `computeFillableMinor` **(corrected 2026-08-14, `ADR 0027`: the cell used to print that same ceiling as a "Falta {amount}" figure, which drifted from the live ceiling the control actually wrote whenever another line of the same order already held money — see `docs/design/decisions/0027-allocation-list-figures-partition-never-replicate.md`)**. The order's own balance is instead named once per order block, on the reference line (`FR-05-42a`). The list is ordered by order date descending and the lines of one order stay contiguous. The sheet **does not emit `settlesTarget`**: a settled line is derived from its own arithmetic (`remainingBaseMinor <= 0`), so a zero-amount allocation is never written. The sheet is reachable from the orders list "Por tienda" view (`FR-05-44`) and from the store detail page's "Registrar pago" action (`FRD-04 · FR-04-56`); it is not offered from the order detail, which keeps the single-order inline form (`FR-05-17`).
- `FR-05-42a`: The **"Resto del pedido"** line must be rendered whenever an order's assignable balance exceeds what its products can absorb between them, **regardless of how many products it has**, and its ceiling is computed in the query as `assignableMinor - Σ(products)`, where a product with no known price contributes the order's whole balance (it has no ceiling of its own) and a priced one contributes `basePagableMinor - allocatedMinor`. A single-product order with a unit price plus shipping has a base different from its total and therefore produces this line; without it, part of the payment would be unassignable from the sheet. The line is only a line while it is rendered: once its ceiling reaches zero (an allocation made elsewhere between two loads), an amount typed into it stops counting toward the totals, the CTA and the submitted payload, so no money is ever declared through a row the collector can no longer see or correct. Dropping it must never be silent, and this applies to **any** payable line, not only the rest line: whenever a live draft holds money typed into rows the list no longer renders (a refetch that succeeds and comes back shorter is the everyday way there, with the list perfectly loaded throughout), the sheet must name the amount that fell away, shut the CTA until the collector acts on it, and offer to drop just those keys instead of the whole draft. In particular a submission whose declarations were ALL dropped must never take the optimistic-close path: closing there would register the payment on the store's account with every hand-typed line discarded and nothing said.
- `FR-05-42b` **(extended 2026-08-10):** A submission closes the sheet optimistically **only when it carries no declarations**. With at least one declaration the sheet stays open with the CTA in a loading state until the server answers and, on a refusal, keeps the whole draft and marks the specific line the server refused (`createStorePaymentAction` propagates `orderId` / `orderItemId`). A multi-line draft is not reconstructible from a toast, which is what justifies the exception to the default optimistic confirmation. Not every refusal names a line, so the sheet must also handle the ones that do not: a refusal with no `orderId` (`STORE_DEBT_EXCEEDED`, `ALLOCATION_SUM_EXCEEDS_PAYMENT`, `unauthorized`, `server_error`) must be shown **inside the sheet**, not only through the coordinator's toast (which renders behind the modal), and must disable the CTA until the **amount, date or currency** changes, since those are the inputs such a verdict is about and resending an otherwise unchanged draft can only earn the same refusal (editing a line cannot lift it, so a line edit must not re-arm it either). A submission that gets **no answer at all** (a dropped connection, a 502 from the server-actions endpoint) is the opposite case and is treated as one: nothing was refused, so the sheet says so but leaves the CTA live for an identical resend, the coordinator rolls its optimistic patch back, and the sheet releases its loading state, so the modal is never left undismissible with the draft trapped inside it. The two are told apart by an explicit **`unanswered`** flag on the outcome, never by whether the promise rejected: both coordinators deliberately absorb a rejection into a resolved `{ ok: false }` (a `catch` chained after their success handler would roll a payment the server actually committed back off the screen), so a sheet reading the rejection would put every real network drop in the branch that shuts the CTA. A promise that **does** reject anyway is a third case and gets the opposite treatment: with both coordinators absorbing rejections, the only live way there is one of their own success handlers throwing, which means the server already answered (the payment is committed, or it was refused and a resend earns the identical refusal), so the sheet says the outcome could not be confirmed and shuts the CTA instead of inviting the resend. **Known seam, deliberately not closed:** `createStorePayment` takes no idempotency key, so treating an `unanswered` submission as resendable trades a frozen CTA for the chance of a duplicate payment. Most shapes are covered by what happens around it (the invalidated list is refetched with the balances already reduced, after which either the dropped-lines notice or the order/product ceilings shut the CTA, or the server refuses the second attempt), but a payment carrying **no declarations** and small against the store's debt gives neither side anything to object to and can be recorded twice. This is the accepted trade, not a solved case: recovering the draft is worth more than the duplicate is expensive, and the duplicate is visible and deletable from the store's payment list. Closing it properly needs a request key on the mutation (see Open Questions). Every resolved or rejected mutation retires the sheet's cached order list, and it is **refetched in place** when the sheet is still open, so the collector never corrects a line against ceilings the sheet itself has just declared stale. That refetch **keeps the orders already on screen** while the new ones fly (and falls back to them if the new ones never land): a hand-typed draft only exists as long as the rows it was typed into do, so emptying the list for the length of a round trip would take the draft off the screen, kill the CTA and lose the pointer to the refused line. A payload kept after a failed refresh is **marked stale**: the sheet says the list could not be refreshed and offers a retry that refetches over the rows rather than emptying them, since the only other way to ask again is closing the sheet, which costs the draft.
- `FR-05-42c` **(added 2026-08-15, order-detail breakdown):** The order detail's **inline payment form** adopts a SUBSET of `FR-05-42b`, and the subset is a requirement of its own rather than a footnote on that one, because the two surfaces adopt different halves and a single rule with exceptions would read worse than two rules. **Adopted:** a submission closes the form optimistically **only when the breakdown is folded or its draft is empty**; with a draft the form stays mounted with the CTA in its loading state until the server answers, keeps the whole draft on a refusal, and marks the line the server named (`addPaymentAction` now propagates `orderItemId`, which `addOrderPayment` used to discard; `orderId` is NOT propagated because on this door it is always the order being paid). A refusal that names no line is shown **inside the form** and disables the CTA until the **amount or the date** changes (there is no currency to change: an order's currency is fixed), and editing a breakdown line does not re-arm it, since the verdict was never about a line. **It is shown in the words the refusal deserves, `STORE_DEBT_EXCEEDED` included (corrected 2026-08-15):** that one names the STORE and what is still owed it across every order, neither of which exists inside a form scoped to one order, so the coordinator hands the resolved sentence back with the outcome rather than having it interpolated from props dragged through two surfaces. It used to live only in the coordinator's toast, which this same rule switches off while the form is mounted, so with a breakdown on screen the collector read the generic "no se pudo registrar el pago" for a refusal the server had named precisely. A submission that gets **no answer at all** carries the same explicit **`unanswered`** flag: the coordinator wraps the action in a `try/catch` and resolves `{ ok: false, unanswered: true }`, the form releases its loading state, says the outcome could not be confirmed and leaves the CTA live for an identical resend. Without that wrapper a dropped connection rejects a promise nobody catches and pins `isPending` at `true` forever, which on mobile is an undismissable sheet with the draft trapped inside it. **One rule decides who reports a refusal, for both breakpoints: the form's inline error is authoritative and the coordinator's toast fires only when the form is already gone**, i.e. only on the optimistic path. That also retires a defect of its own, where desktop showed the same refusal twice. **Discarded, with reasons:** the third case (a promise rejecting AFTER the server answered) is not modelled here — this coordinator's success handler does `setPayments` plus `router.refresh()`, both idempotent, so the only realistic route to a rejection is transport, which is exactly `unanswered`, and a fourth branch would be dead state in a fifteen-line handler. The dropped-lines / `staleOrders` / refetch-in-place apparatus is not adopted either: it exists for a list spanning several orders that can shrink under the draft, whereas these lines are the products of ONE order loaded with the page and the panel has no refetch of its own. A product vanishing under the draft (another tab) earns `ITEM_ORDER_MISMATCH`, whose copy says to reopen the form. **Known seam, same trade accepted:** `createStorePayment` still takes no idempotency key, so a resent `unanswered` submission can duplicate a payment; here the duplicate is born on the very order the collector is looking at, in the same card, with its own delete button, and recovering the draft is worth more.
- `FR-05-43` **(revised 2026-08-09, revised 2026-08-20, `ADR 0033`):** A payment's own amount must never exceed what the collector currently owes its store in the payment's currency (`StoreDebtRow.debtMinor` = Σ `totalCost` of the store's non-cancelled orders − (Σ the store's payments − Σ `PaymentAllocation.amountMinor` left declared against one of the store's own `CANCELLED` orders, i.e. money kept as `lost` at cancel time per `BR-05-15`), in that currency); exceeding it is refused (`STORE_DEBT_EXCEEDED`) rather than silently accepted as a further credit. - `FR-05-48` **(added 2026-08-13):** The orders list "Por tienda" view (`FR-05-44`) must let the collector mark arrivals from the list itself, not only navigate out of it. - `FR-05-48a` **(added 2026-08-13):** A live selection must be intersected with the server's own list on every resync, and again on rollback, keeping only products that are still listed AND still eligible; when nothing marked survives, the selection is dropped entirely. - `FR-05-48d` **(added 2026-08-13):** The confirmation dialog must never be able to reappear on its own. - `FR-05-47` **(added 2026-08-11):** The orders list must offer a **"Solo con saldo pendiente"** filter (`?balance=true`) that returns the orders whose declared allocations do not cover their own total (`totalCost > allocatedAmountMinor`), always excluding `CANCELLED` orders whatever the status filter says, because a cancelled pedido owes nothing (`ADR 0025`: debt is `Σ committed non-cancelled − Σ paid`).   **Why a filter and not a sort or a dashboard alert.** The collector's question was "how do I _see which ones_ they are", which is an isolation question: a sort would rank the whole list and, with zero matching pedidos today, would rank nothing to the top and prove nothing; a dashboard figure would report a number without a way to open it. **Why it lives inside the filter drawer** rather than as a toolbar control: the toolbar's canonical order (`Buscar < Filtrar < Ordenar < Agrupar < Nuevo pedido`) is at its width budget after the 2026-08-11 redesign, and this is a refinement of a list, not a mode of it, which is exactly what the drawer is for. It costs zero horizontal space and reuses the existing applied-count badge and removable chip.

The filter and `FR-05-35a`'s chip are preventive: the defect they close was invisibility, and invisibility is only cheap to fix before it costs something again.

### Declared payment coverage per producto (added 2026-08-14 — see `docs/design/decisions/0026-declared-product-payment-coverage.md`)

- `FR-05-49` **(added 2026-08-14):** The product must let the collector mark **one producto as paid without committing an amount** (`OrderItem.paidDeclaredAt`), from the orders list "Por tienda" view (`FR-05-44`) and from the order detail's Productos subcard. The mark is a claim, not a figure: it is reversible with the same control, it is never written by a derivation, and it moves no money anywhere (`BR-05-19`). **Revised 2026-08-14 (F2):** the mark is offered **only where there is no number to use instead** (no `unitPrice`, not the single producto of its pedido, no money declared against it, pedido not `CANCELLED`), on every surface alike. Where the exact figure is known the figure is the answer, and offering a claim beside it creates two sources of truth about the same producto; that argument does not depend on the surface, so the order detail now applies the rule the payment sheet already did (`ADR 0026`, amended). An **existing** mark is always rendered and always removable, priced or not, funded or not, cancelled or not (read-only there, with the reason on hover): no mark is ever trapped. A producto that no longer offers it renders **nothing**, not a disabled control. Availability is otherwise blind to delivery state, because entregado and pagado are different axes and the order detail is the only surface where a producto already delivered can still be audited for payment. The mark carries no history entry (`ADR 0025` point 8: a payment writes none, and a claim is less than a payment).
- `FR-05-50` **(added 2026-08-14):** A producto's payment state must be resolved by one shared rule, in this precedence: **(0)** its order's declared allocations cover its own mandatory `totalCost` → "Saldado"; **(1)** its own price base is covered by money declared against it → "Saldado"; **(2)** it carries the mark → "Saldado · marcado"; **(3)** it has a price base and some money declared → progress bar with a percentage; **(4a)** no price base but money declared against it → the **amount** is stated on its own, never a percentage and never a bar (no denominator, no ratio); **(4b)** no price base and no money → the mark is offered; **(5)** a price base and nothing declared → nothing (see `FR-05-49`). Case 0 is an **entailment**, not an estimate: because `totalCost` is mandatory, an order that owes nothing cannot contain a producto that owes something, and no centavo is attributed to any producto to reach that conclusion. A mark outranked by case 0 or 1 is never erased; the order detail keeps rendering it so it stays reversible, while the list surfaces state only the proven fact.

### Order-scoped payment breakdown (added 2026-08-15 — see `docs/design/decisions/0028-order-scoped-payment-breakdown.md`)

- `FR-05-52` **(added 2026-08-15):** The order detail's inline payment form must offer a **folded block, "Desglosar entre productos"**, that lets the collector say how much of THIS payment names each product of the order. It renders only when the order has **more than one product** and at least one of them is still payable (a product whose price base is already covered is not offered at all: no checkbox, no field, a "Saldado" chip). It is **closed by default, always** (536 of 626 recorded payments paid the whole balance in one go and name nothing), it sits **after** the date line and **before** the error and the submit, and while the amount field is empty its trigger stays put with the reason beside it rather than disappearing, because a control that vanishes and returns on the first keystroke moves the submit button under the collector's thumb. **Corrected 2026-08-15:** that trigger carries **`aria-disabled` plus a no-op handler and `aria-describedby` pointing at the reason**, never a real `disabled` (which drops it out of the tab order, never reads its name, and leaves the explanation reachable by no input device at all) — the rule `docs/design/interface-patterns.md` §14 states and this same change extended to name this panel. The real `disabled` is kept for the one case that has no reason to give: the submission in flight, where the whole panel is inert. The fill control ("Máx.") follows the same split when nothing of the payment is left for its line. Folded with a draft, the trigger reads the whole answer: "Desglose · {count} de {total} productos · {amount}", where **`{count}` is the number of lines that will be WRITTEN, not the number of boxes ticked** (see `FR-05-53`). **Folding hides the lines, it never withdraws them (added 2026-08-15):** a folded draft is submitted exactly as that summary reads it back, and it is still a draft the form stays mounted for (`FR-05-42b`, §11.2 of the spec) — dropping it on fold made the summary a claim the payload contradicted, money entering undesglosado while the screen said it had not. **A draft the panel is refusing holds the panel open (added 2026-08-15):** when the draft outruns the payment or a line outruns its own price, the submit is dead and both the sentence saying why and the fields that fix it live inside the block, so it cannot be folded out of sight, exactly as the date disclosure unfolds itself on a date the form refuses. One layout serves both breakpoints (the desktop aside is ~300px and the mobile sheet ~327px), with row height and the list's scroll ceiling the only difference. Ticking a box re-runs the split; typing into a line **pins** it and no recalculation may touch it again; a pinned line is released back to the split only when it is empty **on blur**, never on the keystroke that empties it, because releasing on the keystroke means clearing "30.00" to retype fires a split that writes a number into the field with the cursor inside it. **Amended 2026-08-15 (second consumer):** this block is no longer unique to the order detail. The same component now serves every payment row of the image-intake review screen (`FR-11-103`, [ADR 0029](../../../design/decisions/0029-declaring-allocations-against-an-order-that-does-not-exist-yet.md)), so it lives at `orders/_components/share/` and takes a required `instanceId` from which every DOM id it and its rows mint is derived: with several panels mounted at once, module-constant ids crossed `aria-controls`, `aria-expanded` and every `aria-describedby` at the same time. - `FR-05-53` **(added 2026-08-15):** **No figure derived from the payment may be printed inside the product list, and the residual is a computed figure rather than a control.** The budget is named **once**, above the list ("Por repartir {amount}", plus the percentage in by-price mode), and each row prints only static facts about its own PRODUCT: its price, what earlier payments already declared against it, or that it has no price. Rows carry no per-line ceiling: correct line by line, that figure is false in aggregate, because with an empty draft every row's ceiling is the whole payment, so on an order of six unpriced products the list would advertise six times the money that exists. The fill control is therefore a **word ("Máx.")** with the live amount in its accessible name only, and that amount is the same `computeFillableMinor` the control writes. The **residual** ("Sin desglosar {amount}") is likewise computed and shown in the foot, never offered as an editable field: unlike the store payment sheet's "Resto del pedido", where how much of a multi-order payment lands on this order is a real decision, here the whole payment lands on this order by construction, so the residual is a consequence. A ticked line the payment has no room for shows **"Sin espacio en este pago"**, stays ticked (unticking it would be the app undoing the collector's own decision) and is **not sent**, because a zero-amount declaration covers nothing and the server refuses it outright. The panel announces its running total through one debounced `aria-live` region naming both foot lines, since ticking one box rewrites N fields at once. **Amended 2026-08-15 (second consumer):** unchanged in substance, and deliberately so. A proposal to add a FOURTH foot line for the residual of an already-covered product was raised and **rejected** while taking this panel to the intake review screen: it would improve 0 of 267 real multi-product orders, its condition fires on every opening of the panel (the draft is born with nothing ticked), and it breaks **one residual, one reason** while leaving both existing tests green. **The foot of this panel is not touched by that work.** What did change is the surface: the undetailed-pool strip is suppressed on the review screen, where no money has been paid yet and the row that left some undeclared is visible on the same screen with its own foot.
- `FR-05-54` **(added 2026-08-15):** The split rule is **proportional to price**, and it is the default whenever any product of the order carries one: `denom = max(totalCost, Σ precios)`, `pct = P / denom`, and each line takes `pct × precio_i`. That is how the collector actually pays ("uno generalmente da un adelanto a nivel de porcentaje"), and equal parts only adds up when every product costs the same. **Equal parts is the default only when NO product has a price** (209 of 266 multi-product orders), and in that case the mode control is **not rendered at all**: one line explains why instead, because a dead control in four orders out of five is noise. The mode is decided by the ORDER and never remembered between orders or between payments. The rounding rule is part of the requirement and not an implementation detail: the shares are taken in whole currency steps as `min(floor(precio_i × ratio / step), floor(tope_i / step))` from **one ratio computed once**, and the rounding remainder is handed out one step at a time, only to lines still below their own ceiling, by largest fractional part with position breaking ties. Taken literally as `round(pct × precio_i)` the shares do not add up (S/ 150,02 against a payment of S/ 150,00 on the collector's own data). The percentage is printed **once**, next to the budget, rounded to an integer and labelled **"del pedido"** and never "del saldo", because it measures the payment against the order's total while the amount quick-picks measure it against the remaining balance; the two coincide only on an order carrying no undetailed money. **Declared deviation (2026-08-15): that percentage is a property of the PAYMENT against the ORDER, not the ratio the split actually applies.** Its denominator runs over every ELIGIBLE line of the order, while the split's own ratio runs over the lines it is splitting (ticked and not pinned), so ticking a subset, pinning a line by hand or ticking nothing at all leaves the printed figure where it is. That is deliberate: a figure labelled "del pedido" that jumped about as boxes are ticked would be describing the draft, and the draft has the foot for that. The two denominators can only disagree on a **discounted** order (`Σ precios > totalCost`) split over a subset — one order in the collection, and it is settled. **Amended 2026-08-15 (second consumer):** the split rule itself is untouched — `resolveSplitDenominator`, `splitByPriceLines` and the rounding rule are the same code on both surfaces. What the image-intake review screen changes is the VALUE it passes in, not how the value is used: a payment row there is declared against an order under construction, so row k's denominator is the remaining balance raised, where needed, to the sum of its eligible lines' prices ([ADR 0029](../../../design/decisions/0029-declaring-allocations-against-an-order-that-does-not-exist-yet.md) §3, `BR-11-24`). Because that base is no longer the order's total, the printed percentage has to name it: the panel takes a `percentBasis: "order" | "remaining"` prop that selects between "% del pedido" and "% de lo que falta" and **enters no formula**. The order detail passes `"order"` always, so this label and this figure are exactly what they were. The declared deviation above (the printed percentage is a property of the payment against the order, not the ratio the split applies) still holds on both surfaces, and it is the same reason the label names the BASE rather than promising the literal quotient.
- `FR-05-56` **(added 2026-08-16, `ADR 0030`):** The orders list "Por tienda" view (`FR-05-44`) must state, on every pending product row, **when that product's order is expected to arrive**, and must state it with the granularity it was DECLARED with. A range that spans a whole calendar month is rendered as that month ("sep", "sep 2027"), because the order form's own presets write `startOfMonth → endOfMonth` and 48 of the collector's 62 dated windows are exactly that shape; rendering them as "1–30 sep" would return a day-level precision nobody entered. A single stated day, a genuinely irregular range and a range of whole months keep their own shape ("12 jun", "20 sep – 31 oct", "abr – sep 2027"). The year is printed only when it is not the reader's current year, and a window that crosses the year prints both.

  **Revised 2026-08-17 (`ADR 0030` §8) after the collector read the shipped version: the arrival state is ONE slot of text on the row's second line, in one typeface and one size, and only its COLOUR changes.** There is no arrival chip. A late row states its delay **instead of** its estimate, not beside it: on a product that is late, "Esperada 26 jul" asks the reader to subtract and "Atrasado 17 días" is the answer they were subtracting to get, so printing both spends a pill on a question the row can stop asking. Every string in the slot opens a line and is therefore written in sentence case, in both locales. The row resolves to exactly one of **four** states:
  - **`resolved`** — the product's delivery state is `arrived_at_store` or `in_transit`: the slot states the EVENT that answered the prediction, neutral-toned and with **no ventana at all** — "Ya llegó a la tienda" / "Already at the store", or "Ya está en camino" / "Already on its way". **Revised 2026-08-17 (`ADR 0030` §3.1) after the collector read the shipped version and filed it as a defect** ("¿por qué me sale esperada doce de junio y no me sale atrasado, considerando que ya pasó la fecha?"): until then the slot showed the window in the past tense ("Esperada 12 jun"), which states a prediction and never names the event that closed it, while the chip that accounts for it sits three columns away on the desktop grid — and on the two rows whose window is still AHEAD it read as a live promise ("Esperada oct") about a product already on the shelf. The state no longer requires a window either: a product at the store with no window used to fall to `noDate`, so three of the collector's seven at-the-store rows said "Sin fecha estimada" beside four that said something else. **Declared consequence:** this list no longer shows what a store had promised for a product it eventually produced, and the row's position under "Llegada más próxima" is driven by a date it does not print; the order detail holds the window, and the product name links there. An observed delivery event answers the prediction, and a prediction that has been answered must stop being scored: without this the collector's own data renders a delay counter growing over a product sitting on a shelf, and — worse, because it is false rather than merely incoherent — "llega sep 2026" about a product that has already arrived. **This applies to the state the row is SHOWING, not only to the one the server sent (added 2026-08-16):** marking the product ready at the store from the row's own state control switches the line to the neutral past tense on the spot, without waiting for the page to revalidate, and a mark the server refuses restores the delay together with the state.
  - **`overdue`** — the window closed before today: the slot states the delay in `warning`-toned text ("Atrasado 47 días" below 60 days, "Atrasado 7 meses" from there) **in place of** the window, which is no longer printed on that row. The gradation is in the words and never in a second tone: a `destructive` arrival would exist only in this view, and the same order would read amber in the "Por pedido" list, in its detail and in deliveries, and red here. The delay is spelled out here and stays abbreviated ("Atrasado 47d") in the chips of the other lists, where a pill pays for every pixel; the day/month arithmetic and the 60-day switch are shared, only the wording differs. **Declared consequence:** a late row no longer shows WHICH estimate slipped. The order detail holds it and the product name links there.
  - **`scheduled`** — the window is still ahead: "Llega {ventana}", neutral-toned. _(Until 2026-08-17 a `soon` state split the nearest 30 days off from this one to carry an "info" chip reading "Pronto". With no chip left it would have rendered the same sentence as `scheduled` in a different colour, which is the WCAG 1.4.1 violation the chip had existed to prevent, so it was merged rather than recoloured. What is lost is a categorical "this one is close" scannable without reading the month; what replaces it is that the window already says so at a finer resolution, and the view's default sort puts those rows first. It may be brought back only with a sentence of its own, never with a colour.)_
  - **`noDate`** — no window at all: "Sin fecha estimada", neutral-toned, and **not** a link (the product name one line above already leads to the same place).

  The colour is never the only difference between two states: the words differ ("Llega" / "Ya llegó a la tienda" / "Atrasado"), so a reader who cannot see the amber loses nothing (WCAG 1.4.1, `ADR 0006`). Status colour on TEXT takes the calibrated `--{status}-chip-text` alias and never the raw status token, which is a fill value and does not reach AA as text in the light theme.

  _(Superseded 2026-08-17: between 2026-08-16 and that date the arrival state was a chip on the row's FIRST line, which forced two declared deviations from the secondary-chip rule of `docs/design/interface-patterns.md` §8 — the chip sat beside the product name rather than beside the state chip, and a row flagged ineligible after a refused batch (`FR-05-48a`) suppressed its arrival chip so the two pills could never share the line. Neither rule survives: line 1 again holds the name and at most the ineligible flag, and a flagged row now shows that chip **and** its delay, on different lines.)_

- `FR-05-57` **(added 2026-08-17, `ADR 0030` §3.2):** An order whose **every** product has already been observed reaching the store (each item `arrived_at_store`, `in_transit` or `delivered`) must **not** be reported as late, on any surface: not the "Por pedido" list chip, not the order detail's overdue banner or hero chip, and not the "Entrega atrasada" filter (`delLate=true`). `Order.expectedDeliveryFrom`/`To` is the window for the products to reach the STORE — the shipment to the collector carries its own window on the entrega — so an observed arrival answers it, exactly as it does for a single product in the "Por tienda" row (`FR-05-56`). This is the correction of a real reading: `ORD-20260509-02` holds one product, that product had been at Palmito Store since before its 12 jun window closed, and the order still read "Atrasado 2 meses" in the list and opened its detail with an alert banner counting the same delay directly above the product's own "Listo en tienda" pill.

  Three constraints on how it is written:
  - **Every, not some.** An order with one product on the shelf and five still awaited stays late, because about those five it is late for a real reason.
  - **The arrival line needs a third reading, not just a silenced chip.** With the delay suppressed and nothing else changed, the row said "llega 12 jun" in August — a future tense over a past date, worse than the sentence it replaced. Such an order states **"ya llegó a la tienda"** (lowercase there, because that line is embedded after a `·`) in place of both window sentences.
  - **The filter moves with the chip.** Both sit on the same screen, so an order matching "Entrega atrasada" with no overdue chip on it is a defect of the pair, not of either half.

  **Known divergence, recorded rather than fixed:** the dashboard's "Atrasados" tab drops an order as soon as **any** one of its products has moved, so it already excludes these orders and additionally hides three that are genuinely late about the products still coming. Aligning it changes dashboard figures and is a separate decision.

- `FR-05-55` **(added 2026-08-15):** The orders list "Por tienda" view (`FR-05-44`) must offer a **search box** in the same toolbar slot the "Por pedido" view puts its own in (leading the row, to the left of the sort control), matching **store name or pending-product name**. Until now the view had no way to narrow anything: with tens of stores on screen, finding one store or one product meant scrolling the whole list. It is case- and accent-insensitive, it is submitted (Enter or the search button), and it lives in its own URL param (`sq`), never the order view's `q`: the two views search different things and each preserves the other's params inert, so one input's text must not silently re-filter the other body. A store matched **by name** keeps its group whole (the collector named the store; hiding what is inside it answers a question they did not ask); a store matched only **through its products** shows just the matching products, with its open-order count recomputed from the survivors and its "sin desglosar" list (and the count on its trigger) narrowed to the orders still represented. **The store's debt figure never moves with the search**: what a store is owed is a fact about the store, not about the subset on screen. An active search is stated below the toolbar as an **applied-filter chip** carrying the text and an X that clears it, the same way the "Por pedido" list states its own filters: what is narrowing a list must be visible on the list, not only inside the input that produced it. It is the view's only chip, so no "Limpiar filtros" link sits beside it, the X is the clear-all. No match renders a "Sin resultados" state whose only action clears the search. Because the mobile row now leads with the search box, the store view's sort moves there from a `Select` to an **icon trigger opening the options in a sheet** (the order view already treats sort as a control you open on mobile, inside its filter drawer), which also makes both views' mobile rows the same three slots at the same widths.

### Store-level payment assignment and open-order debt (added 2026-08-20, see `docs/design/decisions/0033-store-debt-scoped-to-open-orders.md`)

- `FR-05-58` **(added 2026-08-20, `ADR 0033`):** On the **store payment sheet** (`FR-05-42`) the sum of what is entered in the Asignación panel must equal the payment's own amount before the payment can be submitted: this tightens the existing `<=` ceiling (`ALLOCATION_SUM_EXCEEDS_PAYMENT`, `FR-05-43`) into an equality on this surface only (`BR-05-31` keeps the order-scoped inline form, `FR-05-17`, at `<=`, since money entered there can never be orphaned). A remainder the collector cannot attribute is not left implicit: it must be sent to the store's own parked pool through the deliberate "no sé todavía" action (`FR-05-60`), which counts toward the sum.
- `FR-05-59` **(added 2026-08-20, `ADR 0033`):** Assignment inside the store payment sheet is done by choosing **products**, never by choosing orders directly; each line's `orderId` is derived from the product the collector picked, mirroring the existing payable-line shape of `FR-05-42`. A product belongs to exactly one order, so naming the product is never less informative than naming the order, and the collector recalls "the One Piece manga", never the autogenerated `ORD-YYYYMMDD-NN` that names it (`FR-05-67`). Naming a product still does not require it to have a price (`FR-05-42a`'s no-price handling is unchanged): naming is not pricing.
- `FR-05-60` **(added 2026-08-20, `ADR 0033`):** The sheet must offer an explicit **"no sé todavía"** action that parks part of the payment against the store, in that currency, without attributing it to any order or product. Parked money is visible on its own as a store-scoped figure and is never counted toward paying down any order's balance until it is later assigned (`BR-05-27`); it functions as the suspense/bridge account a collector-facing accounting flow needs for money known to have moved without yet knowing where it belongs. The action must be chosen on purpose, never defaulted into: a mandatory field with no honest way out produces a guessed product, and a wrong attribution corrupts one order silently, which is worse than an amount that is visibly unassigned.
- `FR-05-61` **(added 2026-08-20, `ADR 0033`):** The store debt figure shown to the collector, per currency, must count only the store's **open** orders (every non-cancelled order that is not yet `COMPLETED`); a fully delivered order leaves this figure together with its own payments (`BR-05-26`). Partially delivered orders (`PARTIALLY_DELIVERED` and the in-transit statuses) remain inside the calculation, because not every item has been delivered yet. Today this is a no-op against the collector's real data (there are zero `COMPLETED` orders with a balance), so the change only starts protecting the figure going forward, from the moment a delivered order carries an unregistered payment.
- `FR-05-62` **(added 2026-08-20, `ADR 0033`, revised 2026-08-20: the consumption runs in the money transaction, after the arrival has committed and before the settlement amount is computed):** Marking an order's last product delivered must not let that order close while leaving its store's parked money (`FR-05-60`) orphaned. If the store carries parked money in the order's currency, the app applies `min(order's remaining balance, parked amount)` to that order as a real `PaymentAllocation`, and asks the collector to confirm it ("tienes {X} sin asignar, ¿era de este pedido?"); dismissing the prompt without an answer still applies it. **The consumption belongs to the money transaction, the second one, never to the transaction that records the arrival** (`FR-05-33`, `ADR 0032`): the arrival commits first and unconditionally, and only afterwards does the money transaction run, consuming the parked money **before** it computes and writes the settlement of the "Ya pagué el resto" checkbox (`FRD-08 · FR-08-39`). That order is not incidental: consuming first is what makes the settlement amount correct, since otherwise the shortcut would offer the order's full remaining balance when part of it was already paid. The money transaction must run even when the collector unchecked the box, if there is parked money to consume, and if it fails after its retries the arrival stays recorded. In a batch arrival (`FR-05-48`), the same consumption runs order by order, oldest `orderDate` first, with the resulting allocation shown to the collector before they confirm the batch; it is never split proportionally across the batch's orders (`ADR 0025`).
- `FR-05-63` **(added 2026-08-20, `ADR 0033`):** The ceiling that refuses an over-large payment (`STORE_DEBT_EXCEEDED`, `FR-05-43`) must keep validating against the store's **full** debt, including its `COMPLETED` orders, not the open-order figure of `FR-05-61`. The collector must still be able to register a late payment against an order that has already been delivered; scoping the validation ceiling the same way as the displayed figure would refuse exactly that.

### Store account reconciliation (added 2026-08-20, see `docs/design/decisions/0034-store-account-reconciliation-adjustment.md`)

- `FR-05-64` **(added 2026-08-20, `ADR 0034`, revised 2026-08-20: the adjustment names the orders it writes off, so it can never slide onto an order it never explained; revised again 2026-08-20, `ADR 0034` §3: a line may name a delivered order, without which the action is unreachable at the moment it is offered):** The store detail page must offer a **"Cuadrar cuenta"** action that shows what the app believes is owed **broken down order by order, each with its own remaining balance**, plus any parked money (`FR-05-60`). The breakdown lists every **non-cancelled** order of that store and currency that still carries a balance, its fully delivered ones included, in two separately labelled groups (open orders, and delivered orders that still carry a balance), because the natural moment to square a store is the moment it has nothing open left (`ADR 0034` §7) and 522 of the collector's 565 orders are already `COMPLETED`: restricting the list to open orders would leave the sheet empty exactly when the app proposes the cleanup, and would put the whole back catalogue permanently out of reach while its residue keeps feeding the diagnostic figure (`FR-06-28`). A line on an **open** order lowers the debt figure shown to the collector; a line on a **delivered** order lowers the payment-validation ceiling (`FR-05-63`) and the diagnostic figure instead, leaving the displayed debt untouched because that order is already outside it, and the sheet must say so rather than let the collector read an unchanged figure as a failed write. Both mean the same thing and the ceiling is the same in both cases, since `openBalanceMinor` never reads an order's status (`BR-05-32`). The one status refused is `CANCELLED` (`ORDER_CANCELLED`), whose committed total is outside both figures already. The collector then marks which of those orders are actually settled, or types a smaller remaining balance for one of them, and what they marked is recorded as a **reconciliation adjustment** carrying **one line per order it writes off**, each line capped at that order's own open balance and allowed to be partial. The store-level "so you really owe {amount}" figure is a read-out derived from those marks, never a second field the collector fills in. The app must never choose the lines for the collector: a store-wide amount spread across the open orders by any rule (proportional, oldest first, largest first) is a derivation, and this package forbids derived splits everywhere (`ADR 0025`, `ADR 0028`). The adjustment is its own kind of record and never a payment (`ADR 0034` §2), and its lines are never `PaymentAllocation` rows: it is deliberately invisible to every figure built on allocations, so a write-off can never read as money the collector spent, and it never credits an order's own payment ledger. An adjustment line reduces what the **store** is shown to owe (`FR-05-61`, when its order is open) and the ceiling that validates a new payment (`FR-05-63`, whichever the order's status), and both figures must subtract those lines explicitly, over exactly the orders each figure already counts: an order that is delivered leaves the displayed figure carrying its own adjustment lines with it, on the same rule that already moves its debt and its payments together (`BR-05-26`). It never moves an individual order's own balance: the line scopes the write-off to that order so it dies with it, it does not pay it (`FR-05-35`'s "still owed" chip stays, the one figure that deliberately stays gross under `BR-05-32`). **Revised again 2026-08-20 (`ADR 0034` §3.1, §6):** what a line may write off is the order's canonical open balance (`BR-05-32`), already net of any line written against it by an earlier declaration, and the action is refused outright while the store still holds parked money in that currency (`FR-05-69`), because that money reduces the store's figure while staying invisible to a line's per-order ceiling, so allowing both would subtract it twice.
- `FR-05-65` **(added 2026-08-20, `ADR 0034`, revised 2026-08-20: deletion and direction are stated over the whole declaration, lines included):** A reconciliation adjustment must always: (a) carry **today's date**, never a backdated one, so a stale debt is corrected with a fresh entry instead of rewriting history; (b) be **labelled as an adjustment**, distinguishable on screen and in history from a documented payment; (c) carry a **declared reason**, even "no identificado", when none more specific is known; (d) be **deletable as a whole**, its per-order lines going with it, so that if a receipt later turns up, the adjustment is removed and the real payment recorded in its place, and **re-declarable afterwards**, since a line may name a delivered order (`FR-05-64`): under the earlier open-orders-only rule, deleting an adjustment written against an order that had since been delivered left a residue nothing could ever clear, so deletion was a one-way door pretending to be an undo. There is no editing of a single line: one reconciliation is one declaration made at one moment, so correcting it means deleting it and declaring again. (e) carry **no stored total of its own**: an adjustment's magnitude is the sum of the lines that exist, derived when it is read, so the order-deletion cascade can never leave a declaration claiming more than its surviving lines write off, and no caller can send a total that disagrees with them. It is refused in the direction "the collector owes more than the app believes" (`BR-05-30`), on the declaration and on every line of it: that direction is a mispriced order, not an unrecorded payment, and is corrected by editing the order instead. A declaration that writes nothing off is refused rather than accepted as an empty adjustment.
- `FR-05-66` **(added 2026-08-20, `ADR 0034`):** The store must keep a visible history of its own reconciliation adjustments. A store that needs repeated reconciliation is showing a systematic recording problem, not one-off carelessness, and the history is what lets the collector notice the pattern.
- `FR-05-68` **(added 2026-08-20, `ADR 0034` §3.1):** The three guards that pin an order in place while money is declared against it must count **reconciliation adjustment lines as declared money**, exactly as they already count `PaymentAllocation` rows, because a line is deliberately not an allocation (`FR-05-64`) and therefore invisible to every check written before it existed. Specifically: (a) `TOTAL_BELOW_PAID` (`FR-05-40`) must refuse a new total below `Σ allocations + Σ adjustment lines`, not below the allocations alone, or lowering the total of an order that was written off drives its open balance negative with no ceiling left to catch it; (b) `CURRENCY_CHANGE_BLOCKED` (`FR-05-46`) must trigger when the order carries an allocation **or** an adjustment line, or a written-off order can be restated in another currency and the write-off crosses currencies, when a store's account is reconciled per currency and never across them; (c) `STORE_CHANGE_BLOCKED` (`FR-05-46`, `BR-05-11`) must do the same, or a written-off order moves to a store that never declared it, leaving the line reducing a store the collector never squared while the order it names is somewhere else. All three read the same canonical figure as everything else (`BR-05-32`), from its complement: what is already declared against the order.
- `FR-05-69` **(added 2026-08-20, `ADR 0034` §6):** The reconciliation write must **refuse** while the store still holds parked money (`FR-05-60`) in the currency being reconciled, with its own error code (`STORE_HAS_UNASSIGNED_MONEY`), decided before its first write and read from the single derivation of the pool the rest of this package already uses rather than a second one of its own. The refusal names the amount and offers the assignment as the way forward ("Tienes {monto} sin asignar en {tienda}. Asígnalo antes de cuadrar la cuenta." / "{store} holds {amount} you have not assigned yet. Assign it before you reconcile the account."). Two reasons stand behind it. **Arithmetic:** parked money already reduces the store's debt figure at its payment's face value, while being invisible to a line's per-order ceiling (a line's ceiling reads allocations, and parked money is not an allocation, `BR-05-27`), so a store with one open order of 180 and 30 parked can write off the full 180 and drive the payment-validation ceiling to −30, which prints a false "a favor 30" (`FR-05-43`) and disables "Registrar pago" with nothing on screen explaining why. Netting the pool out of each line's ceiling is not available as a fix: it would require deciding **which** open orders the pool belongs to, the attribution this package refuses to guess anywhere (`ADR 0025`, `ADR 0028`). **Purpose:** assigning money is always better than writing a balance off, because an assignment records where real money went while a write-off records that the collector could not say, so offering the write-off while an honest explanation sits unassigned in the same store inverts the last-resort ordering `FR-05-64` depends on.
- `FR-05-70` **(added 2026-08-22):** In the Orders list "Por tienda" view, every store group must land **closed**, at every breakpoint, and each closed row must state its own overdue count. The row is one disclosure control: the **entire header row is the target**, its own padding and its chevron included, bought with an `::after` overlay at `inset-0` rather than by the button's own box (which stops at the text and leaves the padding and the chevron, the pixel that most looks like the control, dead). The controls that share the row opt back above the overlay; the chevron is `pointer-events-none` so a press falls through to it. Within the group body the action cluster reads **Registrar pago, Sin desglosar, Ver tienda**: the two money controls sit together, the one that explains an existing figure beside the one that adds to it, and the navigation out of the group last and carries exactly three facts: which store, how much is pending, and how many of its pending products are already late ("15 de 20 atrasados"; the plain product count when none is). The late count is derived through the same `resolveArrivalState` predicate the rows themselves use, never a second derivation, so a header and the rows underneath it can never disagree on the same screen. Rationale, measured at 375px on real collector data (10 stores, 66 pending products): the open default rendered **7,916px of scroll**, nine and a half screens, of which six stores were spending ~185px each to announce a zero balance; closed, the same list is ~1,110px. Closing without the overdue count would have been strictly worse than the open default, because the reason the collector opens this screen is to find what is late.
- `FR-05-71` **(added 2026-08-22):** Below `lg`, the "Por pedido / Por tienda" chooser must render in the **app header**, beside the page title, rather than in the list's own toolbar. It is the one control of this screen that is simultaneously its STATE and its SWITCH, and the page title reads "Pedidos" in both views, so with the chooser removed from sight nothing on screen would answer which view is active. The header is `sticky top-0`, so the answer stays readable with the list scrolled; the toolbar was not, and the chooser cost 94px of the 343 a 375px phone has, which is what truncated the search placeholder mid-word ("Tienda o produc"). The desktop `Select` in the toolbar is unchanged from `lg` up. The header slot admits only controls of this kind: an ordinary action belongs in the content, beside what it acts on.
- `FR-05-72` **(added 2026-08-22):** A store group's per-product row on touch must give the product **name up to two lines** and lay its second line out as exactly two fixed slots, money at the start and arrival at the end. Measured on the same data: 43 of the 66 names were truncated on one line, the longest needing 505px against the 275 one line provides; two lines take that to five. A currency **code** is printed only when the group holds more than one currency with a balance, since a single-currency group's symbol already names it and the suffix costs 29px on every row. The per-item delivery-state control moves to the row's trailing slot and stands down entirely while a selection is active, because marking one product and marking several are the same decision and offering both on one row is what crowded it.

### Identifying orders by date and store, not by code (added 2026-08-20)

- `FR-05-67` **(added 2026-08-20):** Wherever the product needs to name one order to the collector inside a flow (confirmation prompts, batch previews, reconciliation breakdowns, and similar surfaces introduced or touched by `ADR 0032`, `ADR 0033` or `ADR 0034`), it must identify the order by **date and store** ("pedido del 6 de mayo, Pop Dealer Store"), not by its autogenerated `ORD-YYYYMMDD-NN` code, which is meaningless to the collector. The code remains available as secondary metadata, exactly as the order detail header already treats it (see `## Confirmed`), but stops being the default way an order is named to the user. This is a cross-cutting change that touches several existing screens; it ships as part of the same package rather than as a standalone requirement, so no screen introduced by this package regresses to the old naming while another one is fixed.

## Business Rules

- `BR-05-01`: `Open` is the initial order state.
- `BR-05-02`: Order states for MVP are `OPEN`, `PARTIALLY_IN_TRANSIT`, `IN_TRANSIT`, `PARTIALLY_DELIVERED`, `COMPLETED`, and `CANCELLED`. States are derived in priority order: `COMPLETED` → `PARTIALLY_DELIVERED` → `IN_TRANSIT` → `PARTIALLY_IN_TRANSIT` → `OPEN`. `CANCELLED` is set by the cancel mutation and does not re-derive. See WO-02 for the full derivation algorithm and `deriveOrderStatus` function contract.
- `BR-05-03`: Order status is system-derived and must not be edited directly through a status field.
- `BR-05-04`: The order item spreadsheet should prioritize keyboard entry and support row addition plus cell navigation.
- `BR-05-05`: Unit price remains optional because some stores quote only a single order-level total.

Declarations kept at cancel time (`lost`) are preserved through cancellation (`BR-05-15`), so they remain attached to the order and stay visible after reactivation; declarations removed at cancel time (`credit`) do not reappear on this order, though the collector may re-declare the same (still-existing) `StorePayment` against it again from the order detail or the store payment sheet. **Redesign note:** reactivation runs directly without a confirmation modal because it is a reversible action.
- `BR-05-18`: Physical deletion of an order is blocked whenever at least one of its items is linked to a non-cancelled delivery, matching the cancel eligibility rule. The collector must unlink the affected items from their delivery before deleting or cancelling the order.
- `BR-05-19` **(added 2026-08-14, `ADR 0026`):** **A marca de pagado never moves money.** Writing or clearing `OrderItem.paidDeclaredAt` must not change `Order.allocatedAmountMinor`, any figure of a store's debt (`committedMinor`, `paidMinor`, `debtMinor`, `activeCommittedMinor`, `activePaidMinor`, `lostMinor`), any dashboard figure, or the set of pedidos that earn a payment reminder. Two consequences are deliberate and must not be "fixed": marking every producto of a pedido does **not** reduce its saldo pendiente, and a payment reminder still fires for it, because the reminder reads money (`allocatedAmountMinor < totalCost`). The way out of a reminder is to record the payment, not to weaken the reminder; the alternative would turn the marca into a way to silence notices about real debt. Enforced at the mechanism level by `src/test/money-modules-guard.test.ts`, a static scan over the eight modules that produce every money figure: none of them may so much as name the column. A mark and a declared amount may coexist on the same producto, and a mark must **never** make a payment line read-only (that would push the money into "Resto del pedido", which names no producto, manufacturing the very undesglosado money the feature exists to reduce).
- `BR-05-20` **(added 2026-08-14, `ADR 0026`):** **There is no marca de pagado at the pedido level.** `Order.totalCost` is mandatory, so a pedido's outstanding balance is always known and declaring one "saldado sin monto" would be an accounting plug over a number the system already has. The honest equivalent already exists and is money, in one tap on both surfaces: the **"Todo · {amount}"** quick-pick of the inline form and the **"Máx."** fill control of the allocation panel, whose accessible name carries the same amount it writes (corrected 2026-08-14: this rule used to name a "Falta {amount}" quick-pick in the inline form, a label that only ever existed in the allocation panel; **re-corrected 2026-08-14, `ADR 0027`:** that same label was then dropped from the allocation panel's own control, which now prints "Máx." and states the figure only in its accessible name — see `FR-05-42`). Relatedly, order-level money is **named, never split**: `getPendingProductsByStore` sums item-level allocations only, and money with `orderItemId IS NULL` is surfaced as its own per-pedido block (`FR-05-51`). No proportional, chronological or first-producto split may be introduced (`ADR 0025`, and measured at −47% to +72% error on the collector's own data). The amount-less declaration that used to live on `PaymentAllocation.settlesTarget` is deprecated **write-strict / read-tolerant**: `createStorePayment` refuses `settlesTarget: true` with `SETTLES_TARGET_UNSUPPORTED` (checked before the amount rules, so `{amountMinor: 0, settlesTarget: true}` cannot slip past), an allocation amount of `0` is now invalid unconditionally, and every existing read branch is kept so a row arriving out of band still renders as "Saldado" instead of the phantom `S/ 0.00` history row that motivated retiring it.
- `BR-05-21` **(added 2026-08-14, `ADR 0026`):** **Cancelling a pedido with the `credit` choice also clears its productos' marcas de pagado**, in the same transaction that deletes its allocations and resets `allocatedAmountMinor` to `0`; the cancel modal states it in that option ("Las marcas de pagado de los productos también se quitan."). The collector has just unlinked every peso that funded the coverage, so a producto still reading "Saldado · marcado" would claim a coverage nothing pays for, and `BR-05-17`'s reactivation would bring the pedido back full of those claims with zero money behind them. The `lost` choice keeps its allocations and therefore **keeps** its marcas, by the same logic. Separately, a producto that carries a marca cannot be removed in edit or deleted from the pedido: both `replaceOrderItems` and `deleteOrderItem` refuse with `ITEM_HAS_PAID_MARK` (before their first write, per `ADR 0022`), beside the existing `ITEM_HAS_ALLOCATION` guard; the collector removes the marca first. A batch declaration is all-or-nothing: ownership of every id is verified before the write, so a foreign id refuses the whole batch (`ITEM_NOT_FOUND`) rather than silently applying the subset.
- `BR-05-22` **(added 2026-08-15, `ADR 0028`):** **A breakdown never moves the order's balance.** `addOrderPayment` raises the payment against this order and only this order, so `P = Σ product lines + residual` decides how much of the payment NAMES a product and nothing else: `saldoDespués = totalCost − (allocatedAntes + P)` contains no term of the split. Ticking, unticking, re-splitting, typing and clearing must therefore move the breakdown's first foot line ("Desglosado {A} de {P}") and never its second ("Este pedido quedará debiendo {X}"). The panel cannot contradict the balance because it does not take part in computing it.
- `BR-05-23` **(added 2026-08-15, `ADR 0028`):** **The unit of an order's payment ledger is the TRANSFER, not the allocation.** A payment broken down across three products writes N+1 allocations, and one transfer must still render as one row with one delete button; the delete acts on the pair (payment, order) and takes this order's whole claim, leaving a payment shared with other orders alive with theirs. The record's `id` is therefore the payment id, and `orderPaymentDeleteSchema` keeps `min(1).max(64)` rather than narrowing to `cuid()`: 606 of the collector's 626 payments carry a 29-character `mig_*` id from the Notion migration, and deleting is the only correction path they have.
- `BR-05-24` **(added 2026-08-15, `ADR 0028`):** **The residual of a proportional split has a closed form, in TWO terms**: `residual = pct × max(0, denom − Σ precios) + Σ (sobrantes de tope)`, with `denom = max(totalCost, Σ precios)` and `pct = P / denom`, up to rounding at the currency step. **`Σ precios` is qualified (2026-08-15): it runs over the lines the split is running on** (ticked and not pinned), which is the same set `denom` is taken over, so the identity closes against the money actually being placed. The percentage printed beside the budget takes its own denominator over every eligible line of the order instead (`FR-05-54`), and the two are the same number except on a discounted order split over a subset. Both terms are load-bearing and writing it with one would leave half the rule uncodified. The first says the part of a payment that falls on what has no price (shipping, fees, products with no price captured) belongs to no product and stays undetailed rather than being spread across products that did not cause it. The second says money a line cannot take **because its own price is already covered** also leaves the split, and is never handed to the other products: "each product gets the same percentage of its price" is the sentence on screen, and giving B a share derived from A's ceiling contradicts it while the collector is reading it. The one movement that IS permitted is the sub-step rounding remainder, and only inside a stated bound: no line may end above `ceil(su propia cuota)`, which is what separates breaking a tie from redistributing money. **One residual, one reason (added 2026-08-15):** the foot's explanation lines all print the SAME figure, so at most one of them may show. The two terms above are the by-price explanations (`footResidualUnpriced` for the first, `footResidualClamped` for the second); "the ticked products cannot take more" (`footCapped`) is the **equal-parts** explanation and is shown only there, because equal parts does fill every ticked line to its ceiling while by price never offers a line more than its own quota, so pointing at the ceilings would name a constraint that never bound.
- `BR-05-25` **(added 2026-08-16, `ADR 0030`):** **"Today" on the orders list is the collector's CIVIL day, resolved from `User.timezone`, never a wall-clock instant.** Every lateness question on the page compares against `expectedDelivery*`, which is a calendar day stored at UTC midnight; `new Date()` is an instant, and in Lima (UTC−5) it is wrong in both directions (at 10:00 an order due today already reads late; at 21:00 an order due tomorrow does too). Both consumers on the page are bound to the same value — the per-row chips AND the "Atrasados" SQL filter, whose rule is the same one expressed in SQL — because fixing one and not the other puts an order in the filter with no chip on it, on the same screen. The value is computed on the SERVER and travels as a prop; deriving it on the client would also desynchronise hydration. **Extended 2026-08-16 to the order DETAIL**, which resolved its own wall-clock instant: its overdue banner takes `timeZone` from the page and resolves the same civil day, and its private copy of the overdue-days count — floored at `Math.max(1, …)`, so an order due today read "Atrasado 1 día" there and "Atrasado" everywhere else — is replaced by the shared `getOverdueDays`. Both halves had to move in the same pass: correcting the instant while keeping the floor would have left the wrong label on the very rows the fix was for. **Residual limit:** with `User.timezone` null the resolution still falls back to UTC, but the column is now populated rather than left to chance — the app shell captures the browser's IANA zone on first load and backfills collectors who predate the capture, so the fallback only covers a brand-new collector's first render, exactly as it does for the dashboard and the reminders.
- `BR-05-13`: The `Needs currency update` indicator must represent reconciliation state against the collector's current base currency rather than a simple order-status proxy.
- `BR-05-14`: Bulk reconciliation may apply one entered rate to all affected orders within the same currency pair, while preserving order-level manual edits when the user chooses to defer.
- `BR-05-26` **(added 2026-08-20, `ADR 0033`):** A fully delivered order leaves the store's open-order debt calculation together **with its own declared payments**, in the same step. Removing only its committed total while leaving its payments in the store's other figures would push those payments onto whichever other order is still open, understating that order's own debt: the failure the owner traced through the numeric example of `ADR 0033` (a store owing 100 across two 50-total orders, with 30 paid but unassigned, would show the surviving order at 20 instead of 50 once the other order closed and only its total left the sum).
- `BR-05-27` **(added 2026-08-20, `ADR 0033`):** Parked (unassigned) money never reduces any order's or any store's debt figure until it is declared against a specific order or product. It is visible on its own as a store-scoped figure in its own currency, exactly like a suspense/bridge account, and it is not left open indefinitely: closing an order is what drains it (`BR-05-28`), and the store's own reconciliation adjustment (`FR-05-64`) is the last-resort path for whatever a habitually late store never gets around to assigning.
- `BR-05-28` **(added 2026-08-20, `ADR 0033`):** Consuming parked money on order close (`FR-05-62`) always applies `min(order's remaining balance, parked amount)`, and defaults to applying it to the closing order even when the parked money might have belonged to a different order of the same store. This is a deliberate directional choice: attributing money to the wrong order overstates that order's own remaining balance, which the collector sees and can correct; leaving it in the pool understates whichever order is still open, silently, and nothing on screen ever points at the mistake. Overstating debt is a visible error; understating it is the one that corrupts the books unnoticed.
- `BR-05-29` **(added 2026-08-20, `ADR 0034`):** A reconciliation adjustment always carries **today's date** and never edits a past record. A stale or wrong debt figure is corrected the same way a closed accounting period is corrected: with a new entry dated today, never by rewriting the historical one.
- `BR-05-30` **(added 2026-08-20, `ADR 0034`, revised 2026-08-20: the adjustment is its own record, so the one-way rule is declared rather than inherited; revised again 2026-08-20: it is declared on each per-order line as well):** A reconciliation adjustment is only valid in the direction "the collector owes **less** than the app believes." The opposite direction is not a missing payment, it is a cost the order recorded wrong, and is corrected by editing the order's own total, not by an adjustment. This restriction is **declared by the adjustment's own models** and inherited from nothing: an adjustment is stored as its own record with its own per-order lines (`FR-05-64`), never as a `StorePayment` carrying a flag and never as `PaymentAllocation` rows (`ADR 0034` §2, §3), so `StorePayment.amount > 0` says nothing at all about it. The direction is therefore stated three times over: the only stored amount in the record is a line's and it is an unsigned magnitude, with no field anywhere on either table able to express the opposite direction; the database enforces a `CHECK` that the amount is greater than zero on the line table; and the write refuses, before its first write, a declaration that writes nothing off and any line larger than its own order's open balance. **Revised again 2026-08-20 (`ADR 0034` §5): the declaration stores no total at all.** An earlier draft gave it an `amountMinor` column with the invariant "always equal to the sum of its lines", which the order-deletion cascade breaks with nothing in place to notice (delete one of the two orders a 380 adjustment named and the header still claims 380 over 200 of lines; delete both and it claims 380 over none). The magnitude is therefore derived at read time from the lines that exist, which removes the invariant instead of defending it: a cascade lowers it to what is left, and a declaration whose lines have all gone derives zero and subtracts nothing anywhere. Every amount is derived server-side (each line against that order's own server-computed balance) and never accepted from the client, so no caller can invert the direction, and a total that is never stored cannot disagree with the lines it is made of.
- `BR-05-32` **(added 2026-08-20, `ADR 0034` §3.1):** **An order has one canonical open balance, defined in one module of the data layer, and every surface that bounds money against an order or aggregates what is owed reads it.** `openBalanceMinor(order) = order.totalCost − Σ PaymentAllocation.amountMinor − Σ StoreAccountAdjustmentLine.amountMinor`. The adjustment line (`FR-05-64`) is a **third term**, and the write paths that predate it computed a gross balance that stops at the allocations, so two definitions of the same money were briefly in use at once: that is how a written-off balance gets paid a second time, in real money, months later. **Revised 2026-08-20 (same day, fourth review pass): seven consumers are mandatory, not six.** Two were already net and now cite this rule instead of holding their own formula: the ceiling on each new adjustment line (`FR-05-64`) and the store debt figure shown to the collector (`FR-05-61`, which is this same expression aggregated over the store's open orders). Five become net here: the settle-on-arrival amount ([`FRD-08 · WO-08`](../frd-08-delivery-management/bp-01-delivery-management/work-orders/wo-08-settlement-on-arrival.md)), the parked-money consumption when an order closes (`FR-05-62`), the dashboard's obligation figures including the diagnostic `FR-06-28` ([`FRD-06 · WO-07`](../frd-06-dashboard/bp-01-dashboard-aggregation-and-surface/work-orders/wo-07-open-order-debt-and-unrecorded-payment-figures.md)), the three order-edit guards (`FR-05-68`, which read the complement, `Σ allocations + Σ lines`), and **the per order allocation ceiling `EXCEEDS_BALANCE`** (`FR-05-19`), which compares `allocatedAmountMinor + pending` against the raw `totalCost` today and must compare against `openBalanceMinor` instead. That seventh one is the only consumer bounding money the collector types **by hand**, from the order form or the store payment sheet, which makes it the last defence against paying a written-off balance a second time: on an order of 180 written off in full, the gross comparison `0 + 180 > 180` is false, so the allocation is accepted and real money lands in the dashboard's spend and consumed-budget figures. It is owned by the work order that owns the canonical module ([`WO-10`](bp-01-order-domain-foundation/work-orders/wo-10-order-open-balance-and-store-account-adjustment-model.md)), which also means `src/lib/data/orders/storePaymentMutations.ts` is **not** untouched by this package. The figure **cannot be negative by construction**, because each of its three terms is bounded against it before being written (`EXCEEDS_BALANCE` on an allocation, `ADJUSTMENT_EXCEEDS_ORDER_BALANCE` on a line, `TOTAL_BELOW_PAID` on the total), so a negative value can only mean one of those ceilings was bypassed and real money was counted twice: it must be **rendered, never clamped to zero**, since clamping converts the single loud symptom of a double count into silence, which is the failure class `BR-05-28` names as the one that ruins the books unnoticed. This binds **every** reader of the figure, presentation included: no surface in this package clamps it, and where another document instructs a surface to floor a negative balance at zero (`BR-06-08`), this rule governs. Two surfaces deliberately stay gross after this package's eighth-consumer audit: an order's own detail balance and its "still owed" chip (`FR-05-35`) keep reading `totalCost − Σ allocations`, because an adjustment squares the **store's** account and does not pay the order, and the store progress bar's paid-versus-committed visual (`activeCommittedMinor` / `activePaidMinor`, [`FRD-05 · WO-09`](bp-01-order-domain-foundation/work-orders/wo-09-store-payment-assignment-and-open-order-debt.md)) stays a two-ended bar rather than gaining a third "written off" segment, so it visibly under-represents how much of its own gap an adjustment line has resolved. The two readings answer different questions ("did anyone pay this?" stays gross, "may anything still be written against this?" is net), and only the second one bounds a write.
- `BR-05-31` **(added 2026-08-20, `ADR 0033`):** Mandatory full assignment (`FR-05-58`) applies only to the **store-level** payment sheet (`FR-05-42`). A payment added from inside an order's own detail (`FR-05-17`) keeps naming products **optional**, exactly as today: the order is already known from context, so the money it records can never be left orphaned the way a store-wide payment can.

## Acceptance Criteria

### `AC-05-01`

- Given a collector creates a new order
- When the create form opens
- Then the form prefills the order date with the current date
- And the currency defaults to the user's base currency when available

### `AC-05-02`

- Given an order contains quantities and unit prices for every item
- When the user saves a total cost that differs from the derived total
- Then the app shows the discrepancy modal
- And the user can either go back and correct the order or save with the entered total anyway (the entered total is authoritative; see `FR-05-13`)

### `AC-05-03`

- Given an order has an unassigned balance
- When the user adds valid payment records over time
- Then the detail view updates the assigned amount and remaining balance
- And a payment larger than the remaining balance, or larger than the store's own debt, is rejected

### `AC-05-04`

- Given an order is fully delivered but not fully paid
- When the collector views either the list or the detail page
- Then the order shows `COMPLETED`
- And the UI still exposes a clear unpaid warning

### `AC-05-05`

- Given the collector filters the orders workspace
- When they choose store, product type, status, date range, or product-name search inputs
- Then the resulting URL reflects those filters
- And the UI shows removable chips matching the active filter state

### `AC-05-06`

- Given the collector changed base currency
- When they open the orders workspace with pending reconciliation
- Then they can filter affected records using `Needs currency update`
- And completed orders are included when they still impact current or future budget periods

### `AC-05-07`

- Given there are affected orders from multiple source currencies after a base-currency change
- When the collector opens bulk reconciliation
- Then the flow groups updates by currency pair and allows applying one rate per group
- And if the collector skips reconciliation, those orders remain available for manual per-order updates later

### `AC-05-08`

- Given the collector is registering a payment against a store from the store payment sheet
- When the amounts they assign to orders/products add up to less than the payment's own amount, and they do not use the "no sé todavía" action for the remainder
- Then the submission is refused, because a store-level payment must have every part of its amount either assigned to a product or explicitly parked (`FR-05-58`)

### `AC-05-09`

- Given a store has money parked as "no sé todavía" in a given currency
- When the collector views that store's debt, or that store's individual orders, in that currency
- Then none of those figures are reduced by the parked amount until the collector, or the automatic consumption of `FR-05-62`, declares it against a specific order or product

### `AC-05-10`

- Given a store with two open orders A (total 50) and B (total 50), a store debt of 100, and a payment of 30 registered with nothing assigned (parked)
- When the collector marks every product of order A as delivered, closing it
- Then the app applies `min(A's remaining balance, parked amount)`, which is 30, to order A as a real allocation before A leaves the open-order calculation
- And the store's parked money drops to 0
- And the store's displayed debt becomes 50, matching order B's own total exactly, never the understated 20 that leaving the 30 in the pool would have produced

## Implementation Notes

- This FRD consumes base-currency settings from [`FRD-07`](../frd-07-user-settings/frd-07-user-settings.md).
- Order status derivation is owned by this FRD via the pure `deriveOrderStatus` function defined in [`BP-01 · WO-02`](bp-01-order-domain-foundation/work-orders/wo-02-order-item-model-totals-fx-and-derived-order-state-rules.md). The function takes item delivery associations as input and returns the computed `OrderStatus`. [`FRD-08`](../frd-08-delivery-management/frd-08-delivery-management.md) is responsible for invoking `deriveOrderStatus` and persisting the result whenever a delivery state change affects items linked to an order.
- Recorded order totals, item prices, and payment rows remain denominated in the **order currency** (`FR-05-14`); changing the collector's base currency in settings does not rewrite stored order rows. Per-order exchange-rate context (`FR-05-16`, `BR-05-07`) is interpreted relative to the base currency **at the time the order was saved**, which matters for dashboard rollups ([`FR-06-13`](../frd-06-dashboard/frd-06-dashboard.md#functional-requirements); [`FRD-06`](../frd-06-dashboard/frd-06-dashboard.md)).
- The orders list exposes filter label `Needs currency update`, chip label `Currency update needed`, and query-state parameter `fxPending=true`. FX-pending eligibility is **derived**, never stored: an order is pending when its stored `exchangeRate` cannot convert it into the collector's current base currency (`buildNeedsFxReconciliationWhere` in `src/lib/fx/reconciliation.ts`), plus `status != CANCELLED`. The implementation (`FR-05-36`, `FR-05-37`, `FR-05-38`) is owned by [`BP-02 · WO-07`](bp-02-order-workspace-and-list-experience/work-orders/wo-07-currency-reconciliation-filter-and-bulk-fx-reconciliation.md). As shipped, `FxReconciliationModal` lives at `src/app/[locale]/(app)/orders/_components/FxReconciliationModal.tsx` (rendered via `FxAnnouncer`) and is triggered from the orders list banner. The Settings currency-change in [**FRD-07 · BP-01 · WO-05**](../frd-07-user-settings/bp-01-user-settings-identity-and-preferences/work-orders/wo-05-preferences-currency-country-product-types-and-budget.md) writes nothing to orders; it simply moves the base currency the derivation is evaluated against, and offers the optional shortcut to the orders list to reconcile.
- Store selection should reuse the existing shared searchable-select interaction pattern rather than invent a new picker.
- The order identifier format should remain stable across locales even if the human-readable date display changes.
- Orders and deliveries should use expandable cards rather than dense tables because the card format better fits status signals, actions, and mobile layouts.
- The difference between order fulfillment and payment status must remain explicit so dashboard logic can later reason about them independently.

## Lifecycle Interaction Model

Each detail action has a distinct confirmation and feedback contract. The visual treatment of toasts, the undo affordance, the inline Acciones card, and the mobile sticky-bar chrome are owned by the [order FDD](fdd-05-order-payment-shipment.md); this section fixes only the functional behavior. (Mirrors the FRD-08 model so the two workspaces stay consistent.)

| Action                | Confirmation                                                                                                                                           | Apply / feedback model                                                                                                                                                                                                                            | Post-action target                                 |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Save private note     | none (inline autosave on blur, ~800ms debounce)                                                                                                        | **not optimistic** — waits for server confirmation, then shows `"Guardada hace Ns"`; a `NOTE_SAVED` / `NOTE_DELETED` event fires only when the stored value actually changed                                                                      | stays on detail                                    |
| Add payment           | none (inline expand in the Pagos card; mobile sheet)                                                                                                   | optimistic; the hero/ledger update locally and revert with a toast on failure; clearing the balance fires a celebratory toast                                                                                                                     | stays on detail                                    |
| Delete payment        | confirmation modal (`tone-destructive`, `role="alertdialog"`) on the pay-row delete button                                                             | awaited (not optimistic): the modal stays open until the server confirms, then the row is removed and the paid/remaining summary recalculates; no undo affordance                                                                                 | stays on detail                                    |
| Toggle item readiness | none (direct on the item state pill)                                                                                                                   | optimistic flip `NONE` ↔ `ARRIVED_AT_STORE`; reverts on failure                                                                                                                                                                                   | stays on detail                                    |
| Cancel                | confirmation modal (`tone-warning`; optional reason; `credit`/`lost` payments choice when the order carries at least one allocation, `credit` default) | optimistic confirmation: the modal closes on submit and the cancelled state shows immediately; rolls back on failure. **Money is treated as lost and stays declared (`lost`), or is freed as store credit (`credit`, default) — see `BR-05-15`.** | stays on detail                                    |
| Reactivate            | none (reversible, `BR-05-17`)                                                                                                                          | executes directly; returns the order to `OPEN` and re-derives the FX-pending count naturally                                                                                                                                                      | stays on detail                                    |
| Delete                | confirmation modal (`tone-destructive`; type-to-confirm)                                                                                               | awaited (not optimistic, because it is irreversible): the modal stays until the server confirms                                                                                                                                                   | redirects to the orders list                       |
| Edit                  | (separate `/[id]/edit` route)                                                                                                                          | discard-changes guard modal on cancel-with-pending-changes; save is awaited                                                                                                                                                                       | back to detail                                     |
| Create delivery       | (navigates to `FRD-08` create flow)                                                                                                                    | navigation only — no order mutation                                                                                                                                                                                                               | delivery create (`/deliveries/new?sourceOrderId=`) |

Disabled-action rules: `Cancelar` and `Eliminar` share one eligibility gate (`FR-05-24` / `FR-05-25`) — both render disabled with a `title` tooltip when any item is linked to a non-cancelled delivery. In `CANCELLED` state, `Editar` and `Crear entrega` are disabled with an explanatory helper, and `Cancelar` is absent (the order is already cancelled). A `COMPLETED` order has no `Cancelar`.

## Error Contract

Order mutations return typed, expected error codes (string results, not exceptions) so flows can recover without noisy monitoring; unexpected failures are caught once with `Sentry.captureException` and surfaced as `server_error`. Every action also returns `unauthorized` when there is no session. The Zod validation layer (`src/lib/orders/orderValidation.ts`) rejects malformed input before the mutation runs (returning `validation`). Expected domain codes by mutation:

- **create order** (`createOrder`): `STORE_NOT_FOUND`, `INVALID_PRODUCT_TYPE`. With an `initialPayment` (`FR-05-45`), also every `addOrderPayment` code below, mapped back through the same create call.
- **edit order** (`editOrder`): `ORDER_NOT_FOUND`, `ORDER_NOT_EDITABLE` (the order is `CANCELLED`), `STORE_NOT_FOUND`, `STORE_CHANGE_BLOCKED` (store change attempted while the order is not `OPEN`, already has delivery links, or carries a `PaymentAllocation`, per `BR-05-11` and `FR-05-46`), `CURRENCY_CHANGE_BLOCKED` (currency change attempted while the order carries a `PaymentAllocation`, `FR-05-46`), `INVALID_PRODUCT_TYPE`, `ITEM_HAS_LIVE_DELIVERY` (an edited/removed item is linked to a non-cancelled delivery), `ITEM_HAS_ALLOCATION` (a removed item carries a `PaymentAllocation`, `FR-05-46`), `ITEM_PRICE_BELOW_ALLOCATED` (an item's price would drop below what is already declared against it, `FR-05-46`), `TOTAL_BELOW_PAID` (total would drop below `allocatedAmountMinor`, `FR-05-40`), `ITEM_HAS_PAID_MARK` (a removed item carries a marca de pagado, `BR-05-21`). **Added 2026-08-14:** `ITEM_HAS_ALLOCATION`, `ITEM_PRICE_BELOW_ALLOCATED`, `ITEM_HAS_PAID_MARK` and `ITEM_NOT_FOUND` now have their own copy under `orders.error.*`; before this change the first two fell back to the generic message while the server had named the problem precisely. **Added 2026-08-20 (`ADR 0034` §3.1, `FR-05-68`), implemented the same day:** none of these three codes changes name, but all three change what they count. `TOTAL_BELOW_PAID` compares the new total against `allocatedAmountMinor + Σ StoreAccountAdjustmentLine.amountMinor`, not against `allocatedAmountMinor` alone; `STORE_CHANGE_BLOCKED` and `CURRENCY_CHANGE_BLOCKED` trigger when the order carries a `PaymentAllocation` **or** an adjustment line, rather than only the former. A reconciliation line is deliberately not an allocation (`FR-05-64`), so every check written before it existed is blind to it, and these three are the ones where that blindness lets a written-off order be restated, re-homed, or driven to a negative balance (`BR-05-32`).
- **cancel order** (`cancelOrder`): `ORDER_NOT_FOUND`, `HAS_LIVE_DELIVERY_LINKS` (`FR-05-25`). Takes a `paymentsChoice` of `"lost"` or `"credit"` (`BR-05-15`); neither branch produces its own error code.
- **delete order** (`deleteOrder`): `ORDER_NOT_FOUND`, `HAS_LIVE_DELIVERY_LINKS` (`FR-05-24`).
- **reactivate order** (`reactivateOrder`): `ORDER_NOT_FOUND`, `ORDER_NOT_CANCELLED` (only a `CANCELLED` order may be reactivated).
- **add payment** (`addOrderPayment`, order-scoped wrapper over `createStorePayment` — `FR-05-17`): `ORDER_NOT_FOUND`, `EXCEEDS_BALANCE` (declared amount would exceed this order's remaining balance, `FR-05-19`; **revised 2026-08-20, `ADR 0034` §3.1, `BR-05-32`, implemented the same day:** the ceiling is the order's canonical `openBalanceMinor`, net of reconciliation adjustment lines, instead of the gross `totalCost − allocatedAmountMinor`, so a balance already written off cannot be paid a second time by hand. Same code, same copy, one more subtrahend), `STORE_DEBT_EXCEEDED` (payment amount would exceed the store's own debt in that currency, `FR-05-43`; **corrected 2026-08-14:** passed through **unchanged**, no longer collapsed into `EXCEEDS_BALANCE`, so the order detail can name the real ceiling — what is still owed to the store across every order — instead of this order's balance. Two different facts and two different next steps), `AMOUNT_INVALID`, `AMOUNT_FRACTIONAL_SUBUNITS` (a zero-decimal currency received a fractional amount), `DATE_BEFORE_ORDER` (payment date earlier than the order date), `ORDER_CANCELLED`.
- **delete payment** (`deleteOrderPayment`): `NOT_FOUND`.
- **create store payment** (`createStorePayment`, the sheet's own mutation — `FR-05-42`): `AMOUNT_INVALID`, `AMOUNT_FRACTIONAL_SUBUNITS`, `STORE_NOT_FOUND`, `CURRENCY_REQUIRED` (the store has standing orders in more than one currency and none was named), `STORE_DEBT_EXCEEDED` (`FR-05-43`), `ALLOCATION_SUM_EXCEEDS_PAYMENT`, `ALLOCATION_SUM_BELOW_PAYMENT` (**added 2026-08-20, `ADR 0033`, `FR-05-58`, implemented the same day:** raised only when the payment is raised from the store-level surface, where the declared sum plus what is parked must **equal** the payment's own amount; the order-scoped inline form keeps the looser `<=` ceiling and never sees this code, `BR-05-31`), `ORDER_NOT_FOUND`, `STORE_MISMATCH` (a declared order belongs to a different store), `ORDER_CANCELLED`, `CURRENCY_MISMATCH`, `ALLOCATION_AMOUNT_INVALID`, `EXCEEDS_BALANCE`, `ITEM_ORDER_MISMATCH` (also raised when a `declarePaidItemIds` entry is not this collector's or belongs to another store's order, `FR-05-51`), `EXCEEDS_ITEM_BASE`, `DATE_BEFORE_ORDER`, `SETTLES_TARGET_UNSUPPORTED` (`settlesTarget: true` is refused on write, `BR-05-20`; checked before the amount rules).
- **delete store payment** (`deleteStorePayment`): `NOT_FOUND`.
- **create store account adjustment** (`createStoreAccountAdjustment`, the reconciliation sheet's own mutation, `FR-05-64`, **added 2026-08-20, implemented the same day**): `NOT_FOUND` (the store, or a named order outside this collector, store or currency), `CURRENCY_INVALID`, `STORE_HAS_UNASSIGNED_MONEY` (the store still holds parked money in this currency, `FR-05-69`), `NO_ADJUSTMENT_NEEDED` (no line writes anything off), `AMOUNT_INVALID`, `ORDER_CANCELLED` (a line may name any **non-cancelled** order of that store and currency, a fully delivered one included; only `CANCELLED` is refused, and the earlier `ORDER_NOT_OPEN` code is retired before it ever shipped, `FR-05-64`), `ADJUSTMENT_EXCEEDS_ORDER_BALANCE` (a line above its own order's canonical open balance, `BR-05-32`), `DUPLICATE_ORDER_LINE`, `REASON_REQUIRED`. The full enforcement table lives in [`WO-11`](bp-01-order-domain-foundation/work-orders/wo-11-store-account-reconciliation-action.md).
- **delete store account adjustment** (`deleteStoreAccountAdjustment`, **added 2026-08-20, implemented the same day**): `NOT_FOUND`.
- **toggle item readiness** (`setOrderItemArrivedAtStore`): `ITEM_NOT_FOUND`, `ITEM_HAS_LIVE_DELIVERY` (delivery owns the state), `ORDER_CANCELLED`.
- **save note** (`saveOrderNote`): `ORDER_NOT_FOUND`.
- **bulk FX reconciliation** (`updateExchangeRatesAction`): `unauthorized`, `invalid` (Zod: 1–500 updates, each a positive finite rate), `server_error`.

Every refusal above is decided before the mutation's first write, inside its own `$transaction` (ADR 0022); none of these codes can be produced after money has already been persisted.

The store payment sheet adds one code no mutation ever returns: `unconfirmed`, minted client-side when the submit promise itself rejects. That is not a verdict from the server but a failure to read one, so it renders the "we could not confirm whether the payment was recorded" message and shuts the CTA (`FR-05-42b`). The message names the cheap way back out, because the expensive one is the one the collector reaches for on their own: the CTA re-arms as soon as the amount, the date or the currency moves (editing the amount and undoing the edit is enough), so nobody has to close the sheet, and lose a draft of hand-typed allocations, to be able to send again.

Validation-layer bounds (Zod, rejected as `validation` before the mutation): `totalCost` integer in `[1, 999_999_999]` minor units; payment `amount` integer in `[1, 999_999_999]`; `exchangeRate` in `[0.01, 99_999.99]` with two-decimal precision; `currencyCode` length-3 and on the collector base-currency allowlist; order item `name` 1–500 chars, `quantity` integer `>= 1`, `unitPrice` non-negative integer or null; `expectedDeliveryTo` not before `expectedDeliveryFrom` (`DELIVERY_TO_BEFORE_FROM`); payment date not in the future (`PAYMENT_DATE_IN_FUTURE`); note `<= 2000` chars; cancellation reason truncated to 500 chars.

## Analytics

Order events are namespaced under `POSTHOG_EVENTS.ORDER` in `src/lib/constants.ts`. Mutation events carry an `orderId` (and `itemId` / `hasReason` where relevant) but never the free-text note or cancellation-reason value.

- payments: `order_payment_added`, `order_payment_deleted`
- lifecycle: `order_cancelled`, `order_deleted`, `order_reactivated`
- item readiness: `order_item_marked_arrived`, `order_item_reverted_pending`
- note: `order_note_saved`, `order_note_deleted` (emitted only when the stored value actually changed)
- detail navigation / chrome: `order_create_delivery_clicked`, `order_view_store_clicked`, `order_detail_more_menu_opened`, `order_detail_sticky_primary_clicked`
- list: `orders_list_filtered`, `orders_list_filter_chip_removed`, `orders_list_filters_reset`, `orders_list_card_expanded`, `orders_list_card_collapsed`, `orders_list_page_changed`

(The FX reconciliation flow is not separately instrumented under `POSTHOG_EVENTS.ORDER`; it is surfaced via the list FX banner and the shared `FxReconciliationModal`.)

**Store payment sheet (added 2026-08-08, `FR-05-42`):** instrumented under `POSTHOG_EVENTS.STORE` (owned by `FRD-04`, not this FRD, since the sheet is a store-level surface reachable from both the orders "Por tienda" view and the store detail page): `store_payment_sheet_opened`, `store_payment_allocations_opened` (the collector entered the allocation panel, carrying `lines_count`), `store_payment_registered`.

## Screens and Data Contract

Each order route lives under `/{locale}/(app)/orders`. All routes are authenticated: a missing session redirects to `/{locale}/sign-in`. An order that does not belong to the session user resolves to **404** (`notFound()`), never 403, to avoid enumeration. Visual layout is owned by the [FDD](fdd-05-order-payment-shipment.md); this section fixes purpose, data loaded, actions, and states.

### List — `/{locale}/orders`

- **Purpose:** the central collector workspace, opened on the most-recent orders.
- **Data loaded:** chrome first (renders instantly): `getOrderStoreOptions(userId)` (distinct stores the user has orders with, independent of current orderability — mirrors `getDeliveryStoreOptions`) for the filter drawer/chips, plus a suspended heading count (`prisma.order.count` total and closed `COMPLETED`/`CANCELLED`). The suspended data region loads `getOrdersList(userId, filters)` (paginated, 25/page by default — `ORDER_LIST_PAGE_SIZE` = `DEFAULT_PAGE_SIZE`, user-selectable among 10/25/50/100 — `PAGE_SIZE_OPTIONS` — via `?perPage=`; **updated 2026-07-23, owner-approved**, replaces the earlier fixed `30`/page, see [ADR 0018](../../../design/decisions/0018-list-pagination-page-size-and-desktop-summary.md)) which also returns `pendingFxCount`, and the user's `baseCurrencyCode`. When `pendingFxCount > 0`, it additionally fetches up to 500 FX-pending orders (`id`, `humanReadableId`, `totalCost`, `currencyCode`) to seed the reconciliation modal.
- **View toggle (`FR-05-44`, added 2026-08-08):** `?view=order` (default, "Por pedido") or `?view=store` ("Por tienda"); the collector's last choice is remembered via the `ORDER_LIST_VIEW_COOKIE_NAME` cookie, read server-side so the default renders with no client flash. `view=order` renders everything below; `view=store` renders `getPendingProductsByStore(userId)` instead (not paginated — see `FR-05-44` and the pagination-exception note in `docs/design/decisions/0025-store-level-payments-declared-allocations.md`), grouped and two-level sorted by its own `?sort=` domain (`arrival-asc` default, `recent`, `oldest`, `store-asc`, `store-desc`, `total-desc` — a distinct value set from the order-view sort below, sharing the same query param).
- **Search (`view=store`, `FR-05-55`, added 2026-08-15):** `sq` — folded (case- and accent-insensitive) substring match over the store name and the pending products' names, applied in memory over the already-loaded set, before the two-level sort (the ranking is an aggregate over each store's own products, so filtering afterwards would rank stores by products no longer on screen). It is a **separate param from the order view's `q`** and never shares its value: the two match different things and each view carries the other's params forward inert. A store matched by name keeps its group whole; a store matched only through its products shows just those products, with `openOrdersCount` recomputed from the survivors and the "sin desglosar" list narrowed to the orders still represented. The store's debt figure is untouched by the search. No match at all renders a "Sin resultados" state whose CTA drops `sq` and keeps every other param.
- **Filters (URL params, `view=order` only):** `q` (product name / `ORD-…` order code / store name), `productType[]`, `store`, `status[]`, `dateFrom`/`dateTo` (order date), and a single delivery-date mode — `deliveryFrom`/`deliveryTo` (expected-delivery overlap), `delOverdue=true` ("Por recibir": window started and still pending, i.e. in-window or overdue), **or** `delLate=true` ("Entrega atrasada": window fully closed and still pending, the strict overdue subset that mirrors the dashboard's "Atrasados" tab). The three delivery modes are mutually exclusive; the drawer surfaces "Por recibir" and "Entrega atrasada" as a deselectable single-select chip pair (both-off is valid), worded to distinguish "Entrega atrasada" from the delivery-overdue state. Also `fxPending=true`, `balance=true` ("Solo con saldo pendiente", `FR-05-47`), and `sort`. **Status is never auto-applied** — the "Solo activas" entry point hard-codes the four active statuses (`OPEN`, `PARTIALLY_IN_TRANSIT`, `IN_TRANSIT`, `PARTIALLY_DELIVERED`) in its href; a bare `/orders` URL applies no status filter. Sort options: `recent` (default, omitted from the URL), `oldest`, `store-asc`, `store-desc`, `total-desc`. All are native SQL orderings. Every ordering ends in a unique tiebreaker (`id asc`), without which tied rows can reshuffle between two paginated queries and a row is dropped from one page and repeated on the next. _(2026-08-06: `store-desc` added. The set previously offered one direction per dimension, so a collector could ask for `Tienda A–Z` but never `Z–A`.)_ **Removed 2026-08-08 (store-level payments, `FR-05-31`/`FR-05-44`):** the `payment[]` filter (`paid`/`partial`/`unpaid`/`overdue`) and the `payment-asc` sort value are gone — a bare `?payment=` or `?sort=payment-asc` in an old bookmark is silently ignored rather than erroring, falling back to the default. Store debt is now surfaced by the "Por tienda" view instead of a per-order payment-state filter. **Re-added 2026-08-11 in a different shape (`FR-05-47`):** `balance=true` is a binary "still owes money" predicate, not the four-way payment-state filter that was retired; it asks nothing about what fraction of the total is covered.
- **Actions:** navigation only — `Nuevo pedido` → `/new`; each row/card → detail carrying the current list URL via `?returnTo=`. The FX banner opens the bulk reconciliation modal (`updateExchangeRatesAction`). In `view=store`, each group's "Registrar pago" opens the store payment sheet (`FR-05-42`) and a per-group product selection opens the store-scoped arrival modal (`FR-05-48` / `FR-08-38`); those are the two mutation-capable actions on this route. No order mutation happens on `view=order`. `view=store` therefore also loads the collector's `baseCurrencyCode`, which the arrival modal needs, exactly as the `view=order` branch already did.
- **States:** chrome renders immediately; the data region shows a layout-matching skeleton (table desktop / cards mobile in `view=order`, group skeleton in `view=store`, `aria-busy`). Empty initial (`EmptyState appearance="card"`, `PackageOpen` icon in an `accent` well, with the inline `OrderCreateMethodSelector` as its action instead of a single CTA); empty-filtered (`EmptyState appearance="card"`, `SearchX` icon in a `neutral` well, "Limpiar filtros" → bare `/orders`, chips/toolbar retained); `view=store` has its own empty state (no store has a pending product). Empties carry no mascot — see [ADR 0013 · D5](../../../design/decisions/0013-cross-cutting-state-system.md).

### Detail — `/{locale}/orders/[id]` (optional `?returnTo=`)

- **Purpose:** inspect one order, track payments, run lifecycle actions, and launch delivery creation.
- **Data loaded:** `getOrderDetail(orderId, userId)` → order summary, store `{id,name,slug}`, items with a derived per-item `deliveryState` (`open` / `arrived_at_store` / `in_transit` / `delivered`, computed from non-cancelled delivery links + own `OrderItem.deliveryState`), payments (allocations mapped to `paidAmount` / `remainingAmount` / `paymentPercentage` / `hasUnpaidBalance` — `paidAmount` here means **assigned**, `Order.allocatedAmountMinor`), read-only history (newest-first), `eligibility` (`canDelete` / `canCancel` / `blockReason`), and `flags` (`hasPayments`: at least one `PaymentAllocation`; `hasNonCancelledDeliveryLinks`); plus the user's `baseCurrencyCode` for FX display. **Added 2026-08-08:** the page separately loads `getStoreDebtByCurrency(userId, order.storeId)` and passes the store's debt in this order's own currency (`storeDebtMinor`) into the hero, only surfaced when the order itself has no allocation yet (`FR-05-41`). A `returnTo` is sanitized via `safeRelativeReturnTo` and threaded into the back link and downstream store/edit links.
- **Actions:** `addPaymentAction`, `deletePaymentAction`, `setOrderItemArrivedAction`, `saveOrderNoteAction`, `cancelOrderAction`, `reactivateOrderAction`, `deleteOrderAction` (behavior per Lifecycle Interaction Model); `Editar` → `/[id]/edit`; `Crear entrega` → the `FRD-08` create flow; `Ver tienda` → the store page (with `returnTo`).
- **States:** per-status hero (active / overdue / partially-paid / completed-unpaid / cancelled — see the FDD per-state table); read-only History subcard (desktop only); disabled-action helpers for the cancelled and delivery-linked cases; route loading skeleton (`loading.tsx`); 404 when the order is not owned.

### Create — `/{locale}/orders/new` (optional store context, e.g. `?storeId=`)

- **Purpose:** create one store-scoped order via the 3-step wizard (Datos → Productos y costos → Confirmar).
- **Data loaded:** `getOrderableStores()`, the active store product-type keys (`listActiveStoreProductTypeKeys`), and the user's `baseCurrencyCode` (to default the currency field).
- **Actions:** `createOrderAction` (FormData + Zod). On success, navigates to the new order detail (view-transition `order-{id}`).
- **States:** **no-eligible-stores gate** — when the user has zero orderable stores, the route renders `OrderCreateEmptyStores` (CTA → create first store) instead of the form; forward-gated wizard validation; the discrepancy modal (`FR-05-13`, two options) when every item has a unit price and the itemized total differs from the entered total; the "Hoy" exchange-rate prefill (`FR-05-16`); **added 2026-08-08:** the confirm step's optional "¿Pagaste algo hoy?" toggle (`FR-05-45`) with "Pagué todo" / "Adelanto" quick options, amount and date fields.

### Edit — `/{locale}/orders/[id]/edit`

- **Purpose:** adjust an existing order with the all-open (non-wizard) form.
- **Data loaded:** `getOrderById(orderId, userId)` for current values (including `allocatedAmountMinor` to drive the total-below-allocated guard), `getOrderableStores()`, product-type keys, and `baseCurrencyCode`.
- **Guard:** store and currency are **immutable** in edit (rendered read-only with a `lock` icon, `BR-05-11`), and are refused server-side even if the field were forced open whenever the order carries a `PaymentAllocation` (`FR-05-46` / `STORE_CHANGE_BLOCKED` / `CURRENCY_CHANGE_BLOCKED`). A `CANCELLED` order is not editable: the edit route **redirects to detail** (parity with delivery-edit) so the collector must reactivate the order first; `editOrderAction` also rejects with `ORDER_NOT_EDITABLE` as a server-side safety net. The total cannot be lowered below `allocatedAmountMinor` (client + server, `FR-05-40` / `TOTAL_BELOW_PAID`); an item that carries an allocation cannot be removed (`ITEM_HAS_ALLOCATION`) or priced below what is declared against it (`ITEM_PRICE_BELOW_ALLOCATED`).
- **Actions:** `editOrderAction` (bound to the order id). Cancelling with pending changes opens the discard-changes guard modal.
- **States:** 404 when the order is not owned; field validation; discard-changes guard; reactive Resumen rail rendered in the editing (`--warning`) accent.

## State Model

### Order status (`OrderStatus`)

`OrderStatus` is **derived from item fulfillment, never edited through a free field** (`FR-05-32` / `BR-05-03`). The pure `deriveOrderStatus(items)` (in `src/lib/orders/orderState.ts`) maps each item's display delivery state (`open` / `arrived_at_store` / `in_transit` / `delivered`; `arrived_at_store` collapses to `open`) and picks the highest-priority outcome:

`COMPLETED` (all delivered) → `PARTIALLY_DELIVERED` (some delivered) → `IN_TRANSIT` (all in transit) → `PARTIALLY_IN_TRANSIT` (some in transit) → `OPEN` (otherwise / no items).

`CANCELLED` is **never returned by the derivation** — it is set exclusively by the cancel mutation and cleared by reactivate:

| From                | Action                                    | To                                 | Side effects                                                                                                                                                                                                                                                       |
| ------------------- | ----------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| —                   | create                                    | `OPEN`                             | order + items persisted; `ORDER_CREATED` history entry                                                                                                                                                                                                             |
| any non-`CANCELLED` | cancel                                    | `CANCELLED`                        | **declared allocations kept (`lost`) or freed as store credit (`credit`, default)** (`BR-05-15`); the underlying `StorePayment` always survives either way; `cancellationReason` stored; `ORDER_CANCELLED` history; blocked when any item has a live delivery link |
| `CANCELLED`         | reactivate                                | `OPEN`                             | `cancellationReason` cleared; `ORDER_REACTIVATED` history; **allocations kept at cancel time (`lost`) remain attached/visible; allocations freed at cancel time (`credit`) do not reappear, though the collector may re-declare the same payment**                 |
| (derived)           | delivery state change (owned by `FRD-08`) | re-derived via `deriveOrderStatus` | `FRD-08` invokes the pure function and persists the result in the same transaction                                                                                                                                                                                 |
| any (eligible)      | delete                                    | (removed)                          | cascades declared allocations (a payment shared with other orders keeps its `StorePayment` row and other declarations), history, items, and residual cancelled-delivery links; blocked when any item has a live delivery link                                      |

The cancel / delete eligibility gate is identical (`FR-05-24` / `FR-05-25` / `BR-05-18`): both are blocked when any item is linked to a **non-cancelled** delivery.

### Item delivery state (`OrderItemDeliveryState`)

`OrderItem.deliveryState` is a four-value enum: `NONE`, `ARRIVED_AT_STORE`, `IN_TRANSIT`, `DELIVERED`. Within the order domain the collector can only flip `NONE` ↔ `ARRIVED_AT_STORE` (`FR-05-39`); the `IN_TRANSIT` / `DELIVERED` transitions are owned by `FRD-08` (delivery membership). For display, the detail/list queries derive a richer `ItemDeliveryState` (`open` / `arrived_at_store` / `in_transit` / `delivered`) by combining the stored value with live (non-cancelled) delivery links: a live link wins (`delivered` if any linked delivery is `DELIVERED`, else `in_transit`), otherwise the stored `ARRIVED_AT_STORE` shows as `arrived_at_store`, else `open`.

### Payment state (distinct from fulfillment)

Payment progress is tracked separately from `OrderStatus` (`FR-05-33`) and is **never persisted as a status** — `paidAmount` / `remainingAmount` / `paymentPercentage` / `hasUnpaidBalance` are computed at query time from `totalCost` and this order's declared `PaymentAllocation` rows (`calculatePaymentSummary` + `deriveHasUnpaidBalance`; `paidAmount` here means **assigned**, `Order.allocatedAmountMinor`, not a payment ledger the order owns). This is why a `COMPLETED` order can still carry a visible unpaid signal (`FR-05-34` / `FR-05-35`). A new declaration may never exceed the current remaining balance (`FR-05-19` / `EXCEEDS_BALANCE`), nor may the underlying payment itself exceed the store's own debt (`FR-05-43` / `STORE_DEBT_EXCEEDED`); editing the total below the amount already assigned is refused (`FR-05-40` / `TOTAL_BELOW_PAID`). **(Noted 2026-08-20)** payment state and fulfillment state stay independent **by default**; see `FR-05-33`'s 2026-08-20 revision for the one deliberate exception, the delivery-triggered settlement shortcut of `ADR 0032`, which still never writes payment state as a side effect of the same transaction that changes `OrderStatus`.

## Confirmed

- Monetary amounts on an order stay anchored to the order's stored currency; the collector's later base currency preference alone does not retroactively change historical amounts.
- `Order` remains the canonical product term
- the initial order state is `OPEN`
- one exchange-rate value per order is the MVP model
- order note is one inline-editable textarea, not a list of note records
- payment records store amount and date and may be deleted
- **(2026-08-08, revised 2026-08-14)** payments belong to the store, not to a single order; what a payment covers is a separate, optional `PaymentAllocation` declaration (`docs/design/decisions/0025-store-level-payments-declared-allocations.md`); a payment can sit undeclared. Declaring a producto covered **without a known price** no longer goes through `settlesTarget`: that flag is deprecated write-strict / read-tolerant and the claim lives on the producto as `OrderItem.paidDeclaredAt` (`docs/design/decisions/0026-declared-product-payment-coverage.md`, `BR-05-19`…`BR-05-21`), on an axis that carries no amount and moves no figure
- discrepancy handling is a save-time modal, not a passive warning
- order actions in detail view follow the pattern: primary action (`Create delivery`) plus an inline "Actions" card that groups secondary navigation and destructive actions (ADR 0011 replaced the earlier "single More menu" affordance — see `FR-05-23`)
- the order detail header displays store name and order date as the primary title; the human-readable identifier (`ORD-YYYYMMDD-NN`) appears as secondary metadata
- when the collector opens store detail from order detail, the store page back link honors the encoded `?returnTo=` order-detail URL so the collector can return to the same order context instead of falling back to the store listing
- a cancelled order may be reactivated to `OPEN`; allocations kept at cancel time (`lost`) remain attached and visible after reactivation, while allocations freed at cancel time (`credit`) do not reappear on this order, though the underlying payment still exists and can be re-declared (`BR-05-15`)
- cancel and delete share the same eligibility rule: both are blocked when any item is linked to a non-cancelled delivery, so the collector must unlink the item from its delivery before cancelling or deleting the order
- monetary amounts are stored as `Int` in minor currency units (cents × 100); `exchangeRate` uses `Decimal`
- order currency is validated against the same hardcoded allowlist as the user's base currency preference (`ALLOWED_COLLECTOR_BASE_CURRENCY_CODES` in `src/lib/catalog/collectorCountries.ts`); no separate `Currency` database table exists
- reconciliation eligibility is not time-bounded: every non-cancelled order whose stored rate cannot convert it into the collector's current base currency is eligible, regardless of `orderDate` (earlier drafts scoped reconciliation to the current month; that heuristic was dropped because it never converged and left older orders permanently outside both the reconciliation list and the base-currency rollups)
- reconciliation state is **derived per order, never stored**. Each order records `Order.exchangeRateBaseCode`: the base currency its stored `exchangeRate` converts INTO, written whenever a rate is persisted and `null` when there is no usable rate. An order "needs currency update" when `currencyCode != user.baseCurrencyCode` AND (`exchangeRate` is missing or `<= 0` OR `exchangeRateBaseCode != user.baseCurrencyCode`) AND `status != CANCELLED` — the single definition lives in `src/lib/fx/reconciliation.ts` (`needsFxReconciliation` plus the matching Prisma fragment `buildNeedsFxReconciliationWhere`, consumed by `buildFxPendingWhere` in `src/lib/data/orders/orderQueries.ts`). Changing the base currency **writes nothing**: it only moves the value the derivation compares against, so a round trip (`PEN → EUR → PEN`) leaves already-reconciled orders valid instead of re-marking them. Reconciling is **stamping**: order create, edit with a submitted `exchangeRate`, and bulk reconciliation (`updateExchangeRatesAction` → `applyOrderExchangeRates(userId, baseCurrencyCode, updates)`) all write the rate **and** the base it converts into, which is what removes the order from the pending set, so the banner/count converges to zero as the collector works through it. Cancelled orders are excluded from the pending view without changing anything on the row, so reactivating one re-surfaces it. Because the orders list, its count, the modal rows and the dashboard rollup all read this one derivation, they cannot disagree (see ADR 0024 at `docs/design/decisions/0024-fx-reconciliation-derived-from-rate-base.md`; migration `20260803053836_derive_fx_reconciliation_from_rate_base`). The derived state also surfaces as a **per-order indicator** — unchanged in the UI, only its source moved: a `warning` chip (`detail.hero.chipFxPending`) on the order-detail hero next to the status chips (hidden on cancelled orders), and an inline `warning` (`form.exchangeRateOutdatedWarning`) under the edit-form exchange-rate field. Query DTOs still expose a `needsExchangeRateUpdate: boolean`, computed at read time rather than read from a column.
- exchange rate validation for manual input: `min(0.01)`, `max(99999.99)` — consistent with WO-04 and WO-07
- dashboard spend reporting merges delivery shipping cost into the same disbursed-spend figures as order payments, rather than charting it as its own series (comparing the two scales side by side would be disproportionate) — see [`FRD-06 · BR-06-04`, `BR-06-09`](../frd-06-dashboard/frd-06-dashboard.md#business-rules)
- **(2026-08-08, revised 2026-08-09, revised 2026-08-20, `ADR 0033`)** a store's debt (`Σ totalCost` of its non-cancelled orders `− (Σ` its payments `− Σ` `PaymentAllocation.amountMinor` left declared lost against one of its own cancelled orders`)`, per currency) is **not clamped at zero**: a negative value is real money the store holds on the collector's behalf and renders as "a favor" (green), never folded into or confused with the unrelated photo-quota "crédito" veto (`docs/product/glossary.md`). Money declared `lost` at cancel time (`BR-05-15`) is excluded from the paid side of this formula: it is sunk, so it must not count as available money that pays down the store's other orders or turns into "a favor". **As of `ADR 0033` this full formula is the payment-validation CEILING only** (`FR-05-43`, `FR-05-63`), never the collector-facing figure: the number shown to the collector is scoped to the store's **open** orders (`FR-05-61`), so a delivered order leaves the displayed figure together with the payments declared against it (`BR-05-26`), and the two numbers intentionally diverge whenever a completed order still owes money.
- **(2026-08-08)** the orders "Por tienda" view (`FR-05-44`) is a deliberate, scoped exception to the app's otherwise-unified list pagination (`ADR 0018`): it loads the collector's entire pending-product set in one unpaginated, in-memory two-level sort, because at today's real data volume (tens of pending products, not hundreds) that costs nothing and the two-level sort does not translate cleanly to a flat page. See `docs/design/decisions/0025-store-level-payments-declared-allocations.md` for the revisit threshold.
- **(2026-08-08)** `OrderPayment` / `Order.paidAmountMinor` / `Order.paymentPercent` remain in the schema, `DEPRECATED`, unread and unwritten by any live code path; they are kept physically present for reversibility of the store-level-payments trial, not migrated away (`docs/design/decisions/0025-store-level-payments-declared-allocations.md`)

## Open Questions

- whether future post-MVP finance reporting should move exchange-rate context from order level to payment level
- whether `createStorePayment` should take an idempotency/request key, so an unanswered submission can be resent without the chance of a duplicate payment (the known seam recorded in `FR-05-42b`)
- **(added 2026-08-20)** whether the delivery-triggered settlement checkbox (`FRD-08 · FR-08-39`, "Ya pagué el resto") should also appear in the formal shipment flow (the create-delivery wizard and "Marcar como llegada" on the delivery detail), or stay limited to the five "Ya me llegó" quick-arrival launchers (`FRD-08 · FR-08-45`). The formal flow typically has more time elapse between paying and marking the arrival, so if the checkbox is added there it likely should not come pre-checked and should ask for the payment date instead of proposing it. Left open deliberately, not decided by default.

## Cross-domain requirements delivered here

- **Order-side removed-store tombstone (`FR-04-42` / `AC-04-22`, order-side portion of `BR-04-23`).** These requirements are owned by [FRD-04](../frd-04-store-domain/frd-04-store-domain.md): a collector order that references a `REJECTED` store must keep rendering, showing a neutral tombstone message by default and sanction wording only when `Store.removalReason` is the abuse category. The store-side lifecycle (`REJECTED` status, `Store.removalReason`, `isSanctionRemovalReason`) is delivered by [FRD-04 · BP-01 · WO-09](../frd-04-store-domain/bp-01-store-public-trust-system/work-orders/wo-09-store-approval-and-removal.md); the order-side rendering is delivered in this FRD by [BP-02 · WO-08](bp-02-order-workspace-and-list-experience/work-orders/wo-08-order-side-removed-store-tombstone.md), with its design record in [FDD-05 · §5.7](fdd-05-order-payment-shipment.md). The order side only consumes `removalReason`; it never re-classifies removal reasons.
- The equivalent tombstone marker on delivery and dashboard surfaces (which also render a store name and would otherwise show a stale name for a removed store) is a documented sibling follow-up, not part of `WO-08`: `FR-04-42` is scoped to collector orders, and those surfaces will reuse the same `resolveStoreTombstone` helper and `stores.json` copy that `WO-08` introduces.
- **Delivery-triggered settlement's payment write (added 2026-08-20).** [FRD-08](../frd-08-delivery-management/frd-08-delivery-management.md) owns the trigger, the amount calculation, and the reversal of "Ya pagué el resto" (`FRD-08 · FR-08-39`..`FR-08-45`, `BR-08-14`..`BR-08-18`), but the write itself lands entirely inside this FRD's own model: it raises one `StorePayment` (with a new `settledByDeliveryId` column recording provenance) through the same `createStorePayment` path the store payment sheet uses (`FR-05-42`), and it is bound by this FRD's own invariants (`FR-05-61`..`FR-05-63`, and the never-split rule of `ADR 0025`/`ADR 0027`/`ADR 0028`). The range stops at `FR-05-61` on purpose: `BR-05-31` scopes `FR-05-58`, `FR-05-59` and `FR-05-60` (mandatory full assignment, assignment by product, and the explicit "no sé todavía") to the **store payment sheet** (`FR-05-42`), and this write is not raised from that surface. Like the order-scoped inline form, it records money whose order is already known from context, so it keeps the looser `Σ allocations.amountMinor <= amount` ceiling and cannot leave an orphaned remainder. Reopening the delivery that created it deletes exactly that payment (`FRD-08 · FR-08-43`).
