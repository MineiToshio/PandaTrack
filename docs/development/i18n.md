# Internationalization (i18n) with next-intl

## Implemented structure

```
src/
├── app/
│   └── [locale]/                    # Dynamic route segment for locale
│       ├── layout.tsx               # Root layout with NextIntlClientProvider
│       └── (landing)/
│           ├── layout.tsx
│           ├── page.tsx
│           └── _components/
│               └── layout/
│                   ├── Header.tsx   # i18n enabled
│                   └── HeaderNav.tsx # i18n enabled
├── i18n/
│   ├── routing.ts                   # Locales configuration
│   ├── request.ts                   # Server-side configuration
│   └── locales/
│       ├── es/
│       │   ├── common.json          # Shared translations (buttons, etc)
│       │   └── landing.json         # Landing page translations
│       └── en/
│           ├── common.json
│           └── landing.json
└── proxy.ts                         # Request interception for routing
```

## Configured locales

- Spanish (es) - Default locale
- English (en)

## Configuration

### 1. Available locales (`src/i18n/routing.ts`)

```typescript
export const routing = defineRouting({
  locales: ["en", "es"],
  defaultLocale: "es",
});
```

### 2. Messages loading (`src/i18n/request.ts`)

Messages are loaded per file using the defined structure:

```typescript
messages: {
  common: (await import(`./locales/${locale}/common.json`)).default,
  landing: (await import(`./locales/${locale}/landing.json`)).default,
}
```

To add new translation files:

1. Create the file in `src/i18n/locales/es/` and `src/i18n/locales/en/`
2. Add the import in `src/i18n/request.ts`

## Usage in components

### Server Components (default)

```typescript
import { useTranslations } from "next-intl";

export default function Header() {
  const t = useTranslations("landing.header");

  return <button>{t("getStarted")}</button>;
}
```

### Nested namespaces

```typescript
const t = useTranslations("landing.header.nav");

return <Link href="#">{t("features")}</Link>;
```

## Locale URLs

URLs automatically include the locale:

- `/es` -> Spanish (default, may redirect to `/`)
- `/en` -> English

Examples:

- `http://localhost:3000/es`
- `http://localhost:3000/en`

## Add new languages

1. Add the locale in `src/i18n/routing.ts`:

```typescript
export const routing = defineRouting({
  locales: ["en", "es", "ca"], // Add Catalan
  defaultLocale: "es",
});
```

2. Create a `src/i18n/locales/ca/` folder with JSON files

3. Update the matcher in `src/proxy.ts`:

```typescript
export const config = {
  matcher: ["/", "/(es|en|ca)/:path*"], // Add "ca"
};
```

## Add new translation files

Example: add translations for the footer

1. Create files:
   - `src/i18n/locales/es/footer.json`
   - `src/i18n/locales/en/footer.json`

2. Update `src/i18n/request.ts`:

```typescript
return {
  locale,
  messages: {
    common: (await import(`./locales/${locale}/common.json`)).default,
    landing: (await import(`./locales/${locale}/landing.json`)).default,
    footer: (await import(`./locales/${locale}/footer.json`)).default, // New
  },
};
```

3. Use it in a component:

```typescript
const t = useTranslations("footer");
```

## Catalog hygiene

### Locale parity is enforced (`src/test/i18n-locale-parity.test.ts`)

Every namespace file must exist for both locales and expose exactly the same key
paths. A key added to `es` but not `en` is invisible until an English user reaches
that screen, where next-intl renders the raw key path instead of copy. The guard is
a plain set comparison over the JSON on disk, so it cannot report a false positive.

Add, rename, and delete keys in **both** locales in the same change.

### Referenced keys must exist (`src/test/i18n-referenced-keys-guard.test.ts`)

Locale parity catches a key present in one locale and missing from the other. It is
structurally blind to the opposite failure: a key the **code** asks for that **neither**
locale defines. That absence is perfectly symmetric, so the set comparison passes.

The consequence is not a crash. `src/i18n/request.ts` declares no `onError` /
`getMessageFallback`, so use-intl logs and then renders **the raw key path** on screen,
including inside `aria-label`s and button labels. It shipped: the store payment sheet's
allocation panel referenced 46 keys no catalog defined, and the store detail's report
banner two more. Every test stayed green, because the component tests mock `next-intl`
and assert against the key text itself.

This guard is the static scan that closes it. It covers the **two shapes** a key reaches a
catalog through:

1. **A literal key resolved against its `t`'s namespace.** `const t = useTranslations("orders")`
   plus `t("detail.items.title")` must resolve to `orders.detail.items.title` in both locales.
   `getTranslations({ namespace: "…" })` counts too. A variable bound in two component scopes of
   one file yields one candidate per binding and passes when **any** of them defines the key:
   resolving which scope a call sits in needs a real parser, and a guard that cries wolf gets
   deleted.
2. **A refusal code reaching a catalog through a template** — ``t(`error.${result.error}`)``.
   Shape 1 cannot see these, and it is exactly the family whose absence is loudest: the user reads
   "Ocurrió un error inesperado" for a refusal the server named precisely. The union that feeds
   each such surface **is** statically derivable, so `REFUSAL_UNIONS` maps each call site to the
   TS union behind it (hand-traced, because every action in between widens `error` to `string`),
   and every member of every union is required to have copy in both locales. A third test then
   fails on any dynamic `` `…error.${…}` `` surface in the `orders` namespace with no registry
   entry, so adding one without tracing its codes is a red suite rather than silent copy nobody
   checks.

**Its blind spots are declared, not accidental.** A green run proves those two shapes hold, not
that every key exists:

- **A key held in a lookup table** instead of written at the call site. The live example is
  `FILL_DISABLED_KEY` in `StorePaymentAllocationRow.tsx`, a `Record<FillDisabledReason, string>` of
  key paths indexed at render time; its three keys were missing too and were found by hand.
  Recognizing that shape generically means guessing which string literals are key paths, which
  produces false positives on ordinary strings.
- **A `t` whose namespace is not a string literal** (`useTranslations(namespace)`), and every key
  resolved through it: the binding is marked opaque and skipped.
- **Refusal surfaces outside the `orders` namespace tree** (`deliveries.error.*`, `stores.*.error.*`).
  Their unions are relayed through actions that widen `error` to `string`, so each needs its own
  hand-traced entry; they are left unregistered rather than silently treated as covered. Extending
  `REFUSAL_UNIONS` to them is the way in.

Two of its tests exist only to keep it honest: one locks the scan against a refactor that quietly
stops matching (three real fixture shapes), and one reads the **shipped** union declarations rather
than a fixture, so a renamed union fails loudly instead of yielding zero members and passing. If a
union is renamed, update the registry; never drop the entry.

### Finding unused keys is advisory (`npm run find-unused-i18n-keys`)

There is no type-level link between a key and its use: the project does not declare
next-intl's `IntlMessages` type, so `npm run type-check` will not notice a missing
or orphaned key. Deleting copy is therefore a manual judgement, and a plain `grep`
is not enough, because keys are routinely built at runtime:

```ts
t(`detail.history.events.${entry.eventType}`); // template with a static prefix
t(STATE_LABEL_KEY[state]); // object-literal map
tCountries(store.countryCode); // whole namespace is a lookup table
buildPageMetadata({ namespace: "orders", titleKey: "create.title" }); // options bag
```

`scripts/find-unused-i18n-keys.mjs` walks the TypeScript AST and resolves all of
the above (its header lists the full set). It biases every ambiguity toward "used",
so it under-reports dead keys rather than over-reporting them.

It is **not** wired into `npm run test`, on purpose. The analysis is per file, so a
translator passed to a helper in a _different_ module would lose its namespace
binding and its keys would be reported dead. No code does that today, so the tool is
accurate on the current tree, but a routine refactor could make it lie, and a guard
that lies is worse than no guard. Treat its output as candidates and confirm each
one by hand before deleting.
